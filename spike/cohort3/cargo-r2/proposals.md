## The r1 outcome (recorded, `../cargo/explore-r1-transcript.txt`)

The first explore refused: `UNKNOWN child_process_detected (clone3)`,
reproduced on a second run (`../cargo/explore-r1-repro-transcript.txt`,
the machine-readable form: same verdict, same reason). The boundary is the disclosed
forecast exactly: every `cargo add` vforks one child, `rustc -vV`, and
that child creates its internal thread through a raw `clone3` carrying
`CLONE_THREAD` — a thread reached past the pthread wrapper, which the
oracle refuses (the engine's own comment: threads are refused for the
determinism of the subject itself). A refusal is not a FAIL; the define
is not frozen, and this revision exists.

## The apparatus: a RUSTC stand-in (owner-approved, 2026-08-22)

`RUSTC` is cargo's documented configuration ("Instead of running rustc,
run this program"). The stand-in is a single-case shell script (one
match branch, one refusal branch), generated by `ops/setup.sh` (the
bytes that decide the question live inside D2-held files — the hg-r3
rule):

- for argv `-vV` it prints, inline, the exact bytes the image's real
  `rustc -vV` prints (measured 2026-08-22, seven lines, LLVM 22.1.8);
- for ANY other argv it fails loudly (rc 90, the argv named on stderr).

Measured before this revision was written:

1. With the stand-in, `cargo add --offline --path` completes rc 0,
   records the identical manifest entry, and the strace shows **zero
   CLONE_THREAD lines** — the boundary is gone; the remaining child is
   a thread-free `/bin/sh`, which the oracle accounts for.
2. `cargo add` and `cargo generate-lockfile` ask the stand-in for `-vV`
   and nothing else (argv-logged trial).
3. `cargo metadata` asks for much more (`--print=file-names ...
   --print=cfg`, a target-info probe) and dies against the stand-in with
   rc 90 propagated to rc 101 — measured, which is why **the checker
   drops RUSTC** (`unset RUSTC` in `ops/check.sh`): the checker runs
   outside the recording, and its job is stock cargo's own reader. The
   apparatus reaches exactly the recorded operation, nothing else.
4. Setup's cache-warm `cargo metadata` call was removed for the same
   reason; `generate-lockfile` alone creates `.global-cache` and
   `.package-cache` (measured). Setup itself running under the stand-in
   is drilled directly: the drills harness exports RUSTC before calling
   setup, the way the engine's environment will (r1's explore is NOT
   evidence for this — its launcher carried no RUSTC).
