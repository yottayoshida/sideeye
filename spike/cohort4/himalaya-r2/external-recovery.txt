==============================================================
The answer the freeze asked for, and its limits.
==============================================================
   Every sentence here is scoped to the one account configuration this
   script measured: a maildir account with no remote, on this build.
   
   RECOVERY PATHS THAT WERE MEASURED TO WORK:
     1. The content is not lost, so the copy can simply be repeated
        (R4, R7). The source is byte-identical after the crash. The
        repeat does not remove the empty entry: the folder afterwards
        holds both, and the tool lists both as messages.
     2. The empty entry can be moved out of the folder by the tool's
        own delete, once the account names a trash mailbox and that
        mailbox exists (R5). It lands in Trash still at 0 bytes;
        whether emptying the trash removes it was not measured.
   
   THE CONDITION BOTH SHARE:
     Both require the user to notice, and nothing in what was measured
     offers to. No command NAME in the surface is about checking
     stored mail (R1, a scan of names only), the one check-shaped
     command reports the account OK over the damaged store (R2), and
     the one independent maildir reader tried enumerates the empty
     file as an ordinary message (R6). In the tool's own listing the
     entry differs from a real message only by blank columns and 0 B.
   
   THE SYNCHRONIZED SIDE, WHICH THE FREEZE ASKED ABOUT SPECIFICALLY:
     Re-fetching from a server cannot restore the target-folder ENTRY,
     because that entry is never sent anywhere while it is being
     created: the operation makes no call of the traced network class
     (R3, against a positive control on the same filter), and no name
     in the surface is a sync. This is about the entry, not about the
     content: the content may well exist on a server, and it certainly
     still exists in the source folder.
   
     So the maildir-only configuration the freeze names is not the
     only one where a remote side fails to restore the folder state.
     It is where the CONTENT would also be at risk, and this operation
     does not put the content at risk, because it conserves the
     source. That is the honest limit of this finding's severity.
   
   NOT MEASURED, AND STATED RATHER THAN IMPLIED:
     - Whether an EXTERNAL syncer (isync, offlineimap) managing this
       maildir would carry the empty message outward to the server as
       a new message. That is the shape the freeze calls the strongest
       form, the external recovery path itself carrying the damage.
       It needs a second tool and a server, neither in this image.
     - Whether any tool other than the one python reader tried would
       flag the entry.
     - Whether clap's help output is a faithful index of the binary.
       R1's completeness is complete for that mechanism, no more.
