# 測定1: fs_usage は高負荷で行を落とすか

日付: 2026-08-29 / 機械: macOS 15.3.1 (24D70), arm64, **SIP 有効**, APFS, `kern.hv_vmm_present` 0
sideeye 1.0.0 (trace contract v12, Homebrew) / 装置: `loadprobe.c` + `measure1.sh` + `count_writes.py`
生の capture: `runs/drop-*.capture`（10 MB 弱まで committed せず手元）

## 答え: 落とさなかった。毎秒 82 万イベントまで、1 行も

## 結果

| N | shim の記録 | カーネル側の write（state fd） | capture 総行数 | ファイル | 判定 |
|---|---|---|---|---|---|
| 10 | 11 | **10** | 1,877 | 10 bytes | 一致 |
| 100 | 101 | **100** | 2,186 | 100 bytes | 一致 |
| 1,000 | 1,001 | **1,000** | 5,785 | 1,000 bytes | 一致 |
| 10,000 | 10,001 | **10,000** | 41,777 | 10,000 bytes | 一致 |

shim の記録は「N 個の write + 1 個の open」で全段正確。ファイルサイズが地上真実として
一致している（プログラムが実際に N 回書いた）。`unparsed` は全段 0、`state_fds` は全段 1。
実行後に残っていた fs_usage は 0 個。

## 実際に何を耐えたのか（レート）

capture の時刻から測った、目標ファイルへの write が出続けた窓:

| N | 経過 | 目標への write レート |
|---|------|---------------------|
| 1,000 | 0.010 秒 | 約 105,000 writes/秒 |
| 10,000 | **0.048 秒** | 約 207,000 writes/秒 |

N=10,000 の窓（`18:51:42.041862` 〜 `18:51:42.090239`）に入っている **全 capture 行は 39,998**:

```
19999 write      … 目標への 10,000 + shim 自身のトレース 9,999
10000 fstat64    … observer の影（shim が fd を解決する）
 9999 fcntl      … 同上（F_GETPATH）
```

= **毎秒およそ 827,000 イベント。1 行も落ちていない。**

（`fstat64` 10,000 に対し `fcntl` と shim の write が 9,999 なのは窓の端で括りが 1 つ切れている
ため。荷重がかかっているのは目標への write = 10,000 で、これはファイルサイズと一致する。）

## 独立に裏を取った

自分のパーサ（`count_writes.py`、正規表現）だけを信じないため、**別の方法**でも数えた。

1. **総 write 行が全段で `2N + 5`**（25 / 205 / 2,005 / 20,005）。目標への N と shim の
   トレース N と定数 5。パーサが返した N は可変部分のちょうど半分
2. **awk のフィールド位置**で fd 別に数え直し（正規表現を通さない経路）:
   `write F=3` = **10,000**、その他 = 10,005。パーサと一致
3. **アタッチが操作より前**だったことは仮定でなく証拠がある。state ファイルの `open F=3` 行が
   capture に入っている（`18:51:42.041795`、最初の write の 67 マイクロ秒前）

## 設計への帰結

**受領証は「一致した」と書ける。「この範囲では一致した」に弱める必要はない**——ただし
下の「測っていないこと」の範囲で。#181 と `spike/fsusage/RESULTS.md` が「未測定」と
名指ししていた項目が、この構成では埋まった。

## 測っていないこと（主張の範囲）

- **shim を載せた構成でしか測っていない。** shim は各操作を `fstat64` + `fcntl` で挟むので
  目標の進行を遅くする。素の目標ならもっと速くイベントを出せる。**ただし attest は必ず
  shim を載せて走る**ので、測ったのは attest が実際に走る構成そのもの。
  fs_usage の一般的な上限を確かめたわけではない
- **操作は1種類だけ**（1つの fd への 1 バイト write）。作成・改名・削除を混ぜた場合や、
  複数の fd・複数のディレクトリに散る場合は測っていない
- **この機械1台のみ。** APFS、SIP 有効、VM でない。`spike/fsusage/RESULTS.md` の runner
  （macOS 26.5.2、SIP 無効、VM）では測っていない
- **上限は 10,000 操作まで。** それ以上で落ち始めるかは測っていない
- アタッチは 2 秒の固定待ちで、握手ではない。今回は open 行が capture にあることで
  アタッチ済みを確認できたが、これは装置の設計としては弱い（本実装では握手にする）
