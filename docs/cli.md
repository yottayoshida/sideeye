# The CLI in full

The README carries the shortest path to a first verdict. This page carries the rest: the platforms it runs on, installing without Homebrew, every flag and what it refuses, what a saved case is and how replay reads it, a full report with the checker that produced it, and what the declaration is for once the first finding is in.

## What macOS cannot judge

macOS judges less than Linux: it has no seccomp, so no `--observe syscalls` or `--observe supervised`; no strace, so its witness is `fs_usage`, which cannot account for another process; and no cgroup to hold a run in. **A refusal that only macOS raises, and that macOS has no way past, names the Linux run that goes past it, in its message or its `next_step`; where that run is the [CI quickstart](ci-quickstart.md)'s workflow with at most a flag added, it links that page.** Each row below is one such difference; the last rows are walls macOS has a way past of its own.

| What the target does | On Linux | On macOS | The way past |
|---|---|---|---|
| Writes without passing libc's entry points: a raw `syscall(SYS_write, …)`, a stdio flush libc makes from inside itself (a stream left for exit to flush, an `fwrite` past the buffer), `dprintf`, a write glibc splits | counted at the kernel boundary under `--observe syscalls` or `--observe supervised` | refused `oracle_missed_operation`, `child_touched_state_dir`, `state_changed_unaccounted` or, where nothing else was recorded, `state_changed_without_ops` | Linux, under the default mode first and `--observe syscalls` where it refuses the same way; the CI quickstart with the flag added |
| Calls `tmpfile(3)` in the state directory | glibc's creates no directory entry and ignores `TMPDIR`, so it never touches the state | Apple's creates a named file and unlinks it, past the shim: one of the refusals in the row above | Linux, under the default mode |
| Closes every descriptor before it starts another program, the shim's trace among them | counted: the shim puts the trace back on its number, single-threaded and above the relocation floor (ADR 0013, amended 2026-11-01); otherwise refused, and counted under `--observe supervised`, where the engine holds the trace outside the target | refused `unresolvable_path` | Linux; not measured in the CI quickstart |
| Is statically linked, or needs to be counted from outside the process | counted under `--observe supervised` (Linux 5.19 or later, aarch64 or x86_64) | `--observe supervised` and `--observe syscalls` are SETUP ERROR `platform_unsupported` | Linux; not measured in the CI quickstart |
| Starts a child that writes the state | `--oracle <strace>` accounts for the other process | refused `boundary_without_oracle`, with or without `--oracle-fs-usage`; `--allow-unverified` does not lift it | Linux with `--oracle <strace>`; the CI quickstart |
| Makes a call `fs_usage`'s reader does not model, writes through a descriptor the capture never names (a pipe or `socketpair` the target makes itself), or runs so that no thread in the capture wrote the shim's trace | read by strace's reader instead | refused `unsupported_syscall_observed` or `oracle_saw_nothing` | Linux with `--oracle <strace>`; the CI quickstart. On macOS, only the weaker claim: `--allow-unverified` in place of `--oracle-fs-usage` |
| Records for longer than `fs_usage`'s 1800 seconds, or past the 2 GiB of its capture the reader holds | strace has neither limit | refused `oracle_saw_nothing`, naming the limit | Linux with `--oracle <strace>`; the CI quickstart |
| Has a process leave its process group (`setsid`, `setpgid`) | stopped with the run's cgroup and judged, where the engine can make cgroups | refused `child_process_detected` | Linux, where the engine can make cgroups; not the CI quickstart as it stands (below) |
| Declares a recovery that leaves a process running | each recovery command runs in a cgroup of its own, stopped when it exits | not a refusal: only the command's process group is stopped, and a process that left it survives into the next leg | Linux, where the engine can make cgroups |
| Declares a `preload:` apparatus entry (a faked clock through libfaketime) | checked against `/etc/ld.so.preload` | SETUP ERROR `platform_unsupported` | Linux, with the library named there |
| Declares `pin:random` (its randomness pinned by the engine) | the engine preloads its pin library ahead of the shim | SETUP ERROR `platform_unsupported` | Linux, where the engine can make cgroups |
| Gives a path `fs_usage` cuts at its display width | strace prints the whole path | refused `oracle_saw_nothing` | on macOS, a shallower state directory |
| Is an Apple platform binary | — | refused `no_shim_marker`: macOS keeps an inserted library out of it | on macOS, a build of the tool that is not part of macOS (Homebrew's, for example) |
| Is signed with a hardened runtime or library validation | — | refused `no_shim_marker` as a wall | on macOS, a build of the tool signed without them, which the shim can be inserted into |
| Is a framework Python's `bin/python3`, a launcher that replaces itself | — | refused `child_process_detected`, naming the interpreter to run instead | on macOS, that interpreter as the operation's first word |

The cgroup rows are Linux runs the CI quickstart does not reach as it stands: a GitHub-hosted runner's steps start in a cgroup root owns, where the engine makes none, and `docker run`'s defaults mount the cgroup tree read-only (the container rows of [Platforms](#platforms)). The engine makes cgroups where a writable cgroup v2 is delegated to its user, or as root over one; this repository's own CI runs its contained legs through [`spike/in-delegated-cgroup.sh`](../spike/in-delegated-cgroup.sh), which delegates one on GitHub's Ubuntu runners.

## Installing without Homebrew

Take the tarball for your platform from [Releases](https://github.com/yottayoshida/sideeye/releases). Sideeye ships as a binary **and** a shim library, and it looks for the shim beside **itself** — the binary's own canonical path, never the working directory — before `../lib`, so an untarred release runs from anywhere and needs no `--shim` unless you have separated the two files. That search declines a candidate it cannot attribute (a symlink, or a file someone else owns), so an install directory that is not yours alone is refused by name rather than trusted:

```
$ tar xzf sideeye-v1.17.0-aarch64-macos.tar.gz && cd sideeye-v1.17.0-aarch64-macos
$ ./sideeye version
```

Each release asset carries a sha256 GitHub computed when it was uploaded, so checking a download needs nothing published beside it (on Linux, `sha256sum` in place of `shasum -a 256`):

```
$ gh api repos/yottayoshida/sideeye/releases/tags/v1.17.0 --jq '.assets[] | "\(.digest)  \(.name)"'
$ shasum -a 256 sideeye-v1.17.0-aarch64-macos.tar.gz
```

The digest reads `sha256:<hex>`; compare the hex. What this establishes is that the bytes are the ones GitHub holds — not who produced them: the digest and the release are the same account's word, and a checksum file published in the same release would be too.

Or build from source with Zig 0.17.0: `zig build` — binaries land in `zig-out/bin` and `zig-out/lib`, which is the same shape. Whether a newer Zig builds it is checked weekly by [`zig-ahead.yml`](../.github/workflows/zig-ahead.yml), and the breakages already known are listed in [`spike/zig-ahead-known.tsv`](../spike/zig-ahead-known.tsv).

## Usage

Three commands, in the order you will meet them.

**1. See it work** — sixty seconds, nothing to install beyond Sideeye itself:

```
$ sideeye demo
```

The demo writes a small planted-bug tool into a new directory under `$TMPDIR` (or `/tmp`), explores it, and prints a real FAIL report. The tool is built into the binary, so no compiler is needed (#715). The directory is named on the demo's first line and left in place, so the case it saves can be replayed; delete it when you are done. Exit 1 — the planted bug found — is success, which makes the demo double as a smoke test of the binary + shim pair.

**2. Ask whether Sideeye can watch your tool** — before writing any config, and again once you have one:

```
$ sideeye preflight --state <dir> --operation "<cmd>"
```

One observed run: either `recording accepted` (exit 0) or a refusal naming the same detector a real run would use (exit 2). It starts where explore's recording does: the state the setup left is snapshotted, emptied and rebuilt from the snapshot first (#815), so preflight rewrites the state directory too, and takes `--state-under`; with `[controls]` it rewrites it again for each, and leaves the state the recording left, rebuilt — without an owner, a timestamp or an extended attribute the rebuild does not carry. An accepted run — under `--twice`, one whose two runs left the same bytes — ends with a `next` line, the `explore` command for the define it just accepted, ending in what explore on this platform takes. The line carries every flag of that define — `--apparatus` and `--scratch` each as many times as given — and the `--observe`, `--work` and `--state-under` the run was given, and `--shim` when one was given and the mode loads it. It leaves out `--json`, whose file would receive explore's report in place of preflight's document, and `--twice`, which explore does not take. Each word is quoted only where the shell it is pasted into would otherwise change it, so a `$` or a backquote reaches explore as typed; `<your-invariant.sh>` is a placeholder to replace before running it (#823, ADR 0132). What explore on this platform takes is the second witness `--oracle <strace>` on Linux — or nothing, where a strace found on `PATH` was attached, since explore finds it again; `--no-oracle --allow-unverified` after `--no-oracle` —; on macOS, where `--oracle` is refused, `--allow-unverified` — no second witness, the weaker claim, said so in the report — with `--oracle-fs-usage` named in the note above it as the witness macOS has (#702).

Once a `sideeye.toml` exists, the same question takes the toml itself, read as explore reads it:

```
$ sideeye preflight --config sideeye.toml
```

**Every define mistake listed below is refused by `sideeye preflight --config` before any crash world, by the same detector and in the same words `explore --config` uses** — one mistake per run, the first one met, as explore does (#704, ADR 0094):

- the toml does not parse: a syntax error, an unknown key, a value of the wrong shape;
- a `cwd`, `apparatus` or `scratch` entry that does not hold;
- a `state` that is not a directory;
- a `setup`, `operation` or `check` that cannot be started, as the Usage list below defines it;
- a `marker` the recording run does not print (`marker_never_observed`);
- an operation that changes nothing in the state directory, so there is no crash point (`nothing_could_fail`) — explore answers this in the same words when it is given `--oracle` or `--allow-unverified`, and answers the completeness gate first without either;
- for an operation with a crash point, a `check` with no command in it (`--check is empty`), or one declared against a state with nothing in it to corrupt (`checker_not_falsified`);
- in a toml with no `cwd`, run from another directory, a relative argument that is under the toml's directory and not where the commands ran — named, with `cwd = "."` as the line to add.

A `[recovery]` is never run, and the check is not run unless the toml declares `[controls]` (below): the report says each was declared, and a recovery that cannot be started moves no verdict in explore either (ADR 0072). What a world can do differently from the recording is not on the list: an operation that changes the state but nothing the verdict judges can still be refused `nothing_could_fail` by explore, which only a crash world shows. An accepted run's `next` line is `sideeye explore --config '<the toml>'` followed by the run's own flags as above, the toml named in the directory its relative paths were resolved against (a toml that is a symlink keeps its own side); a toml read from `/dev/stdin`, from a shell's `<(…)`, or through a link into `/dev` or `/proc` gets a line saying to save it to a file first, and one whose name cannot be printed as typed a line saying to copy it to a file with a plain name. (zsh's `=(…)` is an ordinary temporary file and is named as one, though it is gone once the command ends.)

**A toml that declares `[controls]` has preflight run them, and report which of the checker's legs each one turned red** (#943, ADR 0143). A control is a command that breaks the state the way one leg of the checker is meant to catch, keyed by that leg's name:

```
[controls]
a = "./break-version.sh"
d = "./break-next-run.sh"
```

Preflight runs them after the recording is accepted (and, under `--twice`, after the two runs agree), each from the state the recording left: the checker first on that state with nothing broken, then, for each control, that state again, the control, and the checker. A control's relative command name is resolved against the toml's directory, and it runs where the define's commands run, with `SIDEEYE_STATE_DIR`; the checker also gets `SIDEEYE_LEGS`, a file to write one `<leg> ok` or `<leg> fail` line per leg to (leg names are letters, digits, `_` and `-`). The text's `controls` block and the JSON's `controls` field give the baseline's word and one word per control — `only_its_leg`, `more_than_its_leg`, `not_its_leg`, `none` (the checker passed the broken state), and the words for what could not be read, `docs/report-schema.md` lists them all. A control that breaks more than its leg is reported, which a hand-written controls script left to its author to notice; whether each leg asks what the target promises is still the author's question. `[controls]` needs `check` and takes the string form only; a leg name is at most 64 characters. Explore reads the section — a `[controls]` with no `check`, or a relative control command under a toml directory holding a space, is refused there as in preflight — and runs none of it. Nothing outside the state is put back between controls, and nothing stops a control or the checker that does not exit, or a process a control leaves running. A checker leg the baseline did not write and a control turned red counts as another leg. The exit code does not move — a control's word is information, not a refusal — unless a control leaves the state where the engine cannot rebuild it (a directory without its owner's write and search bits, for one), which is refused as a world's rebuild would be.

Add `--twice` and it observes the operation twice, each run from the rebuilt pre-state, the second at least two seconds after the first, and compares the two. Byte repeatability is a property of two runs — one observation structurally cannot see it, and a tool that rewrites a timestamp on every run passes everything else preflight asks and is refused only once a full define has been written and explored. Equal post-states: exit 0. Different: the differing paths are named and the command exits 1, which is the negative answer to the question `--twice` asked, not a FAIL verdict — preflight produces none. Under each path it names whose content differs, up to eight of them, a `bytes` line says where the two runs' bytes first differ (a byte offset counted from 0), how long the differing stretch is in each run — what is left once the bytes both runs share at the front and at the back are taken off, widened over shared bytes to a whole UTF-8 character where the first or last difference falls inside a valid one (the line then says where the stretch starts) — what kind of bytes it holds (decimal digits; hex digits, which takes a digit and a letter both; printable text, tabs, line ends and invisible format characters included; or how many bytes fall outside printable text), and quotes both stretches, each clipped at 48 bytes, with every byte outside printable text — tabs and line ends too — and every character that reorders or hides text on a terminal (the bidi controls, the zero-width and invisible marks, tag characters) spelled `\xNN` (#688):

```
difference   nondet.txt (content differs)
             bytes first differ at byte offset 4: first run "1", second run "2" — 1 and 1 byte(s) of 10 and 10, both decimal digits
```

The quoted bytes are in preflight's text output, and — when an oracle ran, named with `--oracle` or a strace found on `PATH` — in the oracle's capture in the work directory, since strace prints the start of what each write wrote; they are not in its `--json` document, which carries where, how long and what kind (below). So wherever the text output or the work directory is kept, a CI log or a committed transcript, those bytes of the state are kept with it. An exploration that refuses `baseline_violates_invariant` over the same difference says where, how long and what kind, and no byte of either stretch, because its message reaches the JSON report, the MCP answer and the reports people paste upstream — and a stretch two runs disagree on is exactly where a per-run token or secret sits. Neither names a cause; [docs/apparatus.md](apparatus.md#reading-a-byte-difference) maps the common shapes to `scratch` and `apparatus`. What it does not establish is that the target is deterministic: the comparison covers file bytes, entry kinds and symlink targets in the state directory (`--state`, or a toml's `[world] state` under `--config`), and two runs are not all runs.

With `--json <path>`, preflight writes what it found as JSON (#717). A refusal or a stop is a report, `sideeye/report`, carrying the refusal the text shows — usually the one `explore` reaches on the same define, though not always (above: with no crash point and no oracle — none named, and no strace found on `PATH` that can trace — and no `--allow-unverified`, explore answers its completeness gate first). An accepted recording, or two runs that differ under `--twice`, is a document of its own, `sideeye/preflight`: the outcome, the account, the set of paths the built-in invariant judges, and under `--twice` each differing path with where, how long and what kind of bytes — never a byte of either run ([docs/report-schema.md](report-schema.md#preflights-document-preflight---json)). The exit code is the same as without the flag.

**3. Explore** — the real thing, with the whole define in one file. The first line is Linux's; the second is macOS's, where `--oracle` (strace) is refused:

```
$ sideeye explore --config sideeye.toml --oracle /usr/bin/strace
$ sideeye explore --config sideeye.toml --allow-unverified
```

```toml
[world]
state = "./state"               # the one directory your tool's state lives in

[define]
setup     = "mytool init"
operation = "mytool rotate-key" # the shim is inserted into this one, not into setup or check
check     = "./check.sh"        # exit 0 = invariant holds; runs after the crash, in a fresh process
marker    = "Recorded"          # optional: the operation's own success claim
expected_status = "3"           # optional: the exit status that means "completed" (default "0")
cwd       = "./repo"            # optional: where the three commands run (default: sideeye's own cwd)
apparatus = ["env:FAKETIME=@2024-01-01 00:00:00", "preload:libfaketime"]   # optional: what the operation's environment must carry
scratch   = ["COMMIT_EDITMSG", ".hg/wcache"]   # optional: paths under state the built-in invariants leave alone
invariant = ["rerun"]           # optional: run the operation again from each crash state

[recovery]                      # optional: the tool's own recovery, run against each saved FAIL
command   = "mytool repair"     # the string form only
check     = "./check-repaired.sh"
```

- The same define works as flags: `--state` / `--setup` / `--operation` / `--check` / `--marker` / `--expect-status` / `--cwd` / `--apparatus` (repeatable) / `--scratch` (repeatable) / `--invariant rerun`. `operation` is **the one command the shim is inserted into**; `setup` and `check` are ordinary commands and may be scripts. What that means for a `#!` script: the kernel hands execution to the interpreter, so the insertion has to reach *that* image rather than the file you named. Whether it can is a property of the interpreter and of the machine — a statically linked one takes no insertion anywhere, and on macOS a platform binary such as `/bin/sh` may have the variable stripped before it starts — so the same define can reach a verdict on one machine and refuse with `no_shim_marker` on another. Naming an executable image directly takes the question away.
- **A setup, operation or check that cannot be started is a SETUP ERROR (exit 3), raised before it runs**, naming the command, the file and which of these it is: the file is missing, is not a regular file, may not be executed by this user (a script needs its execute bit — Sideeye runs `./check.sh`, not `sh check.sh` — or a noexec mount or an ACL denies it), or could not be examined; the `#!` interpreter that file names is one of those; or a bare name has no executable file on `PATH`. A bare name is refused only when every file of that name on `PATH` fails this way, because execvp moves on to the next one. The setup is asked about before it runs, and that refusal leaves nothing on disk; the operation and the check after the setup has run, so a setup may build or write them — but a checker the operation itself would create is refused, so write it in `setup`. The rest: [What the start check leaves unjudged](#what-the-start-check-leaves-unjudged).
- `cwd` is where setup, operation and checker run — **a tool that only works inside its own project (git, most build tools) needs one**, and without it the commands run in Sideeye's own directory. For a tool that refuses to run outside its project that is usually `recording_run_failed`, with the exit status and no cause — or `setup_failed` when `setup` needs the directory too, whose one-line text carries no `cwd` line (the JSON does). The quiet case is worse: a tool that walks up the tree to find its project, as git does, can find a *different* one above Sideeye's directory and succeed there, and nothing refuses. Every report produced after the `cwd` is resolved says which directory the commands ran in: `command_cwd` in the JSON and a `cwd` line in the text — on an UNKNOWN under `next`, in the verdict blocks, and in `preflight`'s report, whose `next` hint carries the `--cwd` it was given — with `(none declared: Sideeye's own)` when nothing was declared (#647). The rest: [Where the commands run](#where-the-commands-run).
- `apparatus` names the devices a deterministic run depends on — a faked clock, a pinned `os.urandom`, a stand-in compiler — so the define is the whole question and the report says what it ran under. Sideeye applies none of it; it checks that each `env:` entry — before `setup` runs, so a setup is not started without the variable — and each `preload:` (a line of `/etc/ld.so.preload`) and `pythonpath:` entry — after `setup`, which may generate them — is present in the environment the operation inherits, and refuses the run as SETUP ERROR when one is not. `note:` entries are carried unchecked. One entry is applied instead: `pin:random` has the engine preload its own library ahead of the shim, so what the operation and its children draw from libc's randomness is the same in every run of one invocation and different in every process — Linux, the default mode or `syscalls`, where the engine can make cgroups (#951, ADR 0146). Recipes, the pin's limits and the one thing to know about global preloads: [docs/apparatus.md](apparatus.md).
- `scratch` names the paths under `state` that nobody depends on — git's `COMMIT_EDITMSG`, a tool's own cache — each entry covering the path itself and everything beneath it. The built-in invariants judge none of them, in no world: not their bytes, not their presence, whether the recording had them before, after, or both, so a torn scratch file no longer decides the verdict and a scratch file whose bytes differ between two clean runs no longer refuses the run. The price is paid in the open: the report carries the declaration verbatim, its `atomicity` line says how many recorded paths the declaration matched, `not tested` names it, and the saved case carries it (a define that declared everything reads `0 path(s) judged pre-or-post` — and, with no checker to judge the worlds instead (a marker has nothing to judge there either), is refused `nothing_could_fail`, because no world in it could have failed (ADR 0091)). What scratch does not silence: a state that changed with no operation recorded, a child the engine could not account for, an entry kind or a file size the snapshot refuses, a tree still being written when it is sampled twice — those are about what the engine observed, not about what is durable. And a checker is still the only thing that says the state is *correct*; scratch only stops the built-in layers from saying it is not (ADR 0043).
- `invariant = ["rerun"]` (or `--invariant rerun`) is a built-in invariant beside the checker or in place of one (ADR 0150). With it, a crash world fails when the operation, run again from its crash state without the shim, ends with an exit status or a state that neither of two reference runs ends with: one from the state before, and one from that run's result. A state is compared on names, kinds and contents; `scratch` is excluded, and so is a path the crash left that the run did not touch (a temporary file under a random name, say), which the `rerun` line counts instead. The two references are built before the worlds, the first twice: an operation that does not end the same way twice from the same state is refused there as `baseline_run_failed`, since nothing fixed would be compared against, and one that varies only by chance can still reach the un-killed baseline world, where the same comparison refuses it as `baseline_violates_invariant`. It is the shape of what the checkers of #861 and #873 did by hand — run the tool again and see whether it succeeds or repairs — and it decides the verdict as a checker does: a FAIL it finds is a FAIL, saved as a case (version 10) that replays with it. Each world runs the operation once more, so it roughly doubles a run's time. The checker's falsification probe does not apply to it, and a FAIL's `reproduce` line rebuilds the crash state without running the operation again there: run it once more by hand to see what the rerun saw.
- `[recovery]` (or `--recovery` with `--recovery-check`) asks a second question about each FAIL: what does the tool's own recovery do to the state the crash left? **Declaring a recovery changes no verdict and no exit code; for each saved FAIL world it adds what the tool's own recovery did when handed that world's crash state — its names, kinds, contents and permission bits (a directory with its owner's bits added), not its timestamps, owners, or set-id and sticky bits.** After the exploration has decided its verdict, and only when there is a FAIL, the recovery checker is first shown a state whose every file holds distinct junk and must reject it, and then the completed, uncrashed state with `command` run on it, and must accept what that leaves; then, for the earliest exhibit and the checker exhibit (once if they are one world), the crash state is rebuilt in `state`, `command` runs, the state is sampled twice to see it has stopped changing, and `check` judges it. The report's `earliest.recovery` and `checker_earliest.recovery` say `pass`, `fail` or `unknown` with the time taken, the `recovery` line says what the result rests on, and the evidence bundle carries the result. `fail` means the recovery ran, ended and was rejected; a recovery that could not be started, exited 125, 126 or 127 (the codes the engine's own child uses before exec), overran `--world-timeout`, left something still writing or running where its cgroup could not stop it, or whose checker accepted the junk or rejected the completed state is `unknown`, never `fail`. The rest: [What a recovery is held to](#what-a-recovery-is-held-to).
- Every define command — setup, operation, check, and a recovery's command and check — finds the state directory in `SIDEEYE_STATE_DIR`: the absolute path of `state`, resolved through any symlink, so a checker reads `"$SIDEEYE_STATE_DIR/…"` rather than a path relative to itself. `TOY_STATE`, the name the demo toy reads, carries the same path to every command, so a checker already written against it runs unchanged (#708). The checker also finds `SIDEEYE_LEGS`: under preflight's `[controls]` a file to write its legs to, and everywhere else a file under the work directory that nothing reads, removed before each run, so a checker that writes to it with `set -u` runs anywhere.
- Every command Sideeye runs — your setup, operation and checker among them — starts with its standard input at end-of-file, on the CLI and MCP paths alike. A target that reads stdin sees EOF, never the terminal or pipe Sideeye itself was started from: that input is the caller's, not the define's, and a committed define has to mean the same run everywhere.
- `--shim` names the interposition library when it is not beside the binary (the tarball and zig-out layouts are found on their own). **A run that found its shim this way names none on its `replay` line or preflight's `next` line** (#827, ADR 0130), so a pasted line runs with the `sideeye` first on `PATH` and the shim found beside its real path, after an upgrade has removed the install it came from too — a `sideeye` that cannot find its own shim refuses, naming `--shim`, and a release whose trace contract changed answers `case_no_longer_applies` for an older case; a run given `--shim` names that path, made absolute when it was given relative ([below](#the-work-directory)). The `reproduce` line runs without Sideeye, so it names the shim's resolved path, and that path goes stale when an upgrade removes it. The search that finds it on its own **declines a candidate it cannot attribute** — a symlink, or a file owned by none of {you, root, the owner of the `sideeye` binary} — and says so rather than using it (#423, ADR 0044); a path you pass here is used as named and not checked. The check is a mitigation, not a boundary: it inspects a pathname, and the dynamic linker resolves that pathname again when the target starts. The rest: [The work directory](#the-work-directory) and [The trace file](#the-trace-file).
- `--json <path>` writes the same report as JSON, for a machine to branch on. **What is at the path when the flag is read is removed only when it is a report Sideeye wrote — a file holding one JSON document, and nothing after it, whose `schema` is `sideeye/report` or `sideeye/preflight`, however it is formatted — or an empty file** (#818). Anything else there — a symbolic link, a directory, a FIFO, a device, the case or the config this same run reads, a log of reports one per line, any other file, or a name whose kind cannot be read — is refused as SETUP_ERROR `define_invalid`, the message naming the path and what it is, and left as it was; that refusal produces no document, so it writes no report, at that path or at an earlier `--json` in the same command, and no `json sha256=` line. The report itself goes through a temporary file this run creates new beside the path, then moves into place. The check reads the name once, when the flag is read: it stops a mistyped path, not a process that can write the directory, and whatever appears at the path during the run is replaced by the report as before. The rest: [The JSON report's digest line](#the-json-reports-digest-line).
- The declared checker's output in each explored world is **also** captured to `<work>/checker-output.txt`, so the evidence bundle can quote the exhibit's last line. On your terminal each line is re-emitted with the world it came from — `world 3: ` for crash point 3, the number the report's `crash point 3 of n` carries, and `baseline: ` for the un-killed world — beside the falsification gate's `falsify: ` lines, the starting-state probe's `start: ` lines when it refuses (#756), and a recovery's `recovery world 3: ` and `recovery world 3 check: ` (its controls are `recovery falsify: `, `recovery baseline: ` and `recovery baseline check: `). The checker's stderr is captured into the same file in the order it was written and comes out on Sideeye's standard output with the same mark, not on Sideeye's standard error (#707). Empty lines are skipped, a line too long for the report's 32 KiB output buffer is dropped with a note on Sideeye's standard error, and a capture over 1 MiB is not re-emitted at all; the file keeps the checker's bytes unmarked, and holds whichever world ran last, which is the un-killed baseline. A capture that cannot be opened does not stop the run: the checker runs uncaptured, its standard output and standard error reach Sideeye's own directly and unmarked, the verdict rests on its exit status as before, and the bundle reports its diagnostic as unreadable, as it does for a capture over 1 MiB.
- `--fresh-state` (replay only) empties and recreates the case's state directory before setup, for a caller that cannot hand over a pristine one — a second replay in the same directory would otherwise die in the leftovers of the first.
- `--leave-crash-state` (replay only) ends the run with the state directory rewritten to what the kill left at the case's crash point, before the checker ran — names, kinds and contents, and permission bits (a directory with its owner's bits added; not set-id or sticky bits, and not the state directory's own mode) — so it can be read as the crash left it instead of rebuilt by hand from the evidence table. It is written after any `--recovery` and whatever the verdict: a replay whose FAIL did not reproduce still leaves the crash state, and the report's `crash state` line and `crash_state_left` say whether it was left and, when not, why — a run that stopped before a verdict leaves none, and a rewrite that fails leaves a FAIL a FAIL. Timestamps and ownership are the rewrite's, two names of one file come back as two files, a directory the engine cannot read comes back empty, and an absolute symlink still points where it did. A process the replay could not contain (a `setsid` child on macOS) that writes after the rewrite changes it silently. `--json` inside the state directory, or in a directory that does not exist yet, is refused with it. Not offered through the MCP server.
- One run at a time in a work directory: a run locks `<work>/run.lock` before `--fresh-state` empties anything and before its setup, and holds it until it exits; a run that names a work directory another run holds is refused as a SETUP ERROR naming that run's pid, before it writes anything there or empties a state (#816). Two runs in one work directory would read each other's traces and reports; give each its own `--work`. `run.lock` has to be a regular file with one link — yours, unless the run just made it — since the run writes its pid into it; anything else there is refused. On a filesystem without locks the lock is skipped and nothing is refused.
- A state directory with anything mounted inside it — a bind mount, a container volume, a disk image — is refused naming the mount point, before anything mounted there is removed: a SETUP ERROR when it is there before the recording run, an UNKNOWN when one appears later. Every world empties and rebuilds the state directory, and what is mounted inside it belongs to another tree (#817). On Linux the mount table (`/proc/self/mountinfo`) is read for this, and a host where it cannot be read is refused the same way; on both Linux and macOS the state is also walked for a directory on another device. A mount point that is the state directory itself is fine; a btrfs subvolume inside it is refused like a mount, because its device differs.
- Exit codes: **0 PASS, 1 FAIL, 2 UNKNOWN, 3 SETUP ERROR** — and UNKNOWN is never 0.
- When standard output is a terminal, `NO_COLOR` is unset or empty and `TERM` is not `dumb`, the text report's verdict word — PASS, FAIL, UNKNOWN, SETUP ERROR — is coloured; otherwise Sideeye adds no escape sequence of its own. Only standard output is asked, so `sideeye explore … > report.txt` typed at a terminal writes no colour to the file; a CI runner that gives its steps a terminal (Buildkite, `docker run -t`) colours the word, and `NO_COLOR=1` turns it off there. There is no flag to force colour (#712).
- `sideeye completions zsh|bash|fish` prints a completion script for that shell: it offers exactly the subcommands; after a subcommand, its positional argument where its usage line has one (a case file, a command name, a shell) and then exactly the flags its usage lines list — explore's and preflight's two lines together, so after `--config` the script still offers `--state`, which the run then refuses — with a value-taking flag's value completed as a file where the usage names a path, as its listed words where it lists them, and not at all otherwise. The script is built from the usage lines `sideeye help` prints, so it offers the flags this binary's help lists. Load it: bash (3.2 and later) `eval "$(sideeye completions bash)"` in `~/.bashrc`; zsh, after `compinit`, `eval "$(sideeye completions zsh)"` in `~/.zshrc`, or the output saved as `_sideeye` in a directory on `$fpath`; fish `sideeye completions fish > ~/.config/fish/completions/sideeye.fish` (#712).
- Command strings split on spaces, no quoting. An argument that carries a space uses the argv form instead: `operation = ["mytool", "commit", "-m", "a message with spaces"]` — one line, passed verbatim. An element of a command's argv form may also be a single-quoted literal string, which has no escapes and carries a `"` as written: `operation = ["sops", "set", "f.yaml", '["k"]', '"v"']` (#949). A space in the directory a `sideeye.toml` sits in is Sideeye's to handle, not yours: a relative `setup`, `operation` or `check` resolved against it runs with that directory and its head as one word. A `[recovery]` command or check, which has only the string form, cannot be: from such a directory a relative one is refused before the setup runs, naming the directory.
- **A string-form command that looks written for a shell runs as written, with a warning** (#706, ADR 0095). Its quotes reach the program as characters, and a whole word a shell would act on — `&&`, `||`, `|`, `|&`, `&`, `;`, `(`, `)`, a redirection such as `>`, `2>&1` or `1>/dev/null`, a word beginning `$` or `~/`, a lone `~`, a backquote, a `$` a shell would expand (one followed by a name, `{` or `(`) anywhere in a word, quoted in double quotes or not, a leading `NAME=value` — reaches it as an argument, unexpanded. Where a setup, operation, check or recovery command (a toml value or a flag) holds a quote or such a word, Sideeye says so in one sentence naming the command and, for quotes, the argv form that groups what they meant (for a flag, as the line a sideeye.toml would take; a `[recovery]` command has no argv form, and neither has a word the argv form cannot spell — an empty one, one holding both `"` and `'`, or one with a `\` — so those are pointed at a script; a word holding a `"` is offered as a single-quoted element). Where a shell would have expanded a `$` or a backquote, no argv is offered: it would carry the unexpanded text. A glob is not looked at, and passes as written either way. The rest: [Commands that look written for a shell](#commands-that-look-written-for-a-shell).
- A define spelled as argv lives in a toml; `preflight --config` reads it, as explore does.
- **A command, option or argument Sideeye does not accept is answered in one line that names what was typed and, when one is close, the nearest spelling that command accepts — never by the whole reference; `sideeye help <command>` (or `sideeye <command> --help`) prints that command's own synopsis and flags** (#705). A value is named as well as a flag (`--observe bogus` says `bogus`). The command's own help carries each flag's first sentence and every sentence of its entry that begins `Caution:`; `sideeye help` prints the whole reference, and `sideeye --version` is `sideeye version`. `sideeye <command> --help` is answered only as those three words: `explore --state X --help` and `explore --help --state X` are refused with that said, because the parser may already have acted on what came before it — `--json` removes the report at its path.

A FAIL saves its counterexample to `<work>/cases/NNNNNN.json`, writes an evidence bundle carrying the same id under `<work>/evidence/NNNNNN.json` — a directory of its own, so a reader of `cases/*.json` is never handed one, and prints the ready-to-paste `sideeye replay` line beside an `evidence` line carrying the command that renders the bundle, `sideeye evidence <bundle>`. The `replay` line carries every flag the run was given that changes how a replay runs or what bounds it — `--observe`, `--shim` when given, `--oracle`, the recovery pair, `--work` when named, `--state-under`, `--allow-unverified` and `--world-timeout` — and leaves the define to the case and `--oracle-fs-usage` off, for the reason in its entry below. Every field of the parsed arguments is classified for this line and for preflight's `next` line, and a field added without a class does not build (#939). The line names the run's own `--work`, so one printed inside a container names the container's directory, and a replay pasted from it writes its traces and captures there, over the run's own — the cases and the evidence bundles it never writes stay. `--state-under` is printed resolved, as the run checked it, and one already on the line refuses a second as given twice. `sideeye evidence <case.json>` renders that bundle as Markdown for a maintainer who has never used Sideeye — the paths whose before, completed and crashed states differ, whether each existed before the operation and whether its old bytes survive elsewhere inside the judged state, the two operations around the crash point, the checker's result and its last output line, the replay command and the run's own caveats. It runs nothing and produces no verdict: exit 0 when it renders, 3 when the bundle cannot be read. Every field is something the run measured or the word `unknown`, and nothing is ranked ([docs/evidence.md](evidence.md)). When some world failed your checker and it is not the overall earliest, that world is saved as its own case beside the first and the text report gains a `checker red` section naming it — two files, both replayable; one file when the two exhibits are the same world, and none of this when no world failed the checker. Replay re-runs the same pipeline restricted to that crash point; when the code changed underneath the case, it says `case no longer applies` instead of guessing. The path you hand it has to be an ordinary file: a pipe, a device or a process substitution is refused rather than read, because a case that cannot be read whole is not a case — and because reading one that never ends would leave the run with no exit code at all (#400). A relative `define.state` inside a case resolves **against the case file's own directory**, the way a relative path in a `sideeye.toml` resolves against the toml (ADR 0007) — so the same case names the same state directory from anywhere, and replay empties the directory the case meant rather than one named by whoever happened to invoke it. Cases this engine saves always store the resolved absolute path, so this rule is about the hand-written ones.

### The flags the define does not spell

Ten flags never appear in a `sideeye.toml`: they belong to the run rather than to the question.

- `--observe wrappers|syscalls|supervised` — where operations are counted. The default, `wrappers`, counts at the interposed libc entry points, with buffered stdio observed at flush granularity. `syscalls` (Linux) counts at the kernel boundary instead, through a seccomp filter and a `SIGSYS` handler inside the target's own process — with `supervised`, one of the two ways to see an operation libc issues from *inside* itself (an `fwrite` past the buffer), or one that never reaches libc at all: a raw `syscall(SYS_write, ...)`, or a runtime like Go's that issues every file call directly. Of the fourteen supported-class rows whose verdict only this mode had reached, `supervised` reached the same verdict on thirteen ([the 2026-10-31 run](../spike/dogfood/2026-10-31-syscalls-under-supervised/RESULTS.md)). Its trap set is every operation that can be a crash point. Check the second entry of the README's constraint list before reaching for it: under this mode an `exec`'d image the shim cannot be loaded into dies at its first state-changing call, which is the one limit that changes what the target does instead of making Sideeye refuse. `supervised` (Linux 5.19 or later, aarch64 and x86_64; #217, ADR 0089) counts the same operations from **outside** the target: the engine starts the operation through `sideeye __filter-exec`, which installs a seccomp user-notification filter and execs it, and no shim is loaded. The rest: [How supervised mode counts, and what it refuses](#how-supervised-mode-counts-and-what-it-refuses) and [A case replays under its own mode](#a-case-replays-under-its-own-mode).
- `--oracle <strace>` — the Linux oracle: the recording run and every explored world are wrapped in strace, and each account is compared against strace's (ADR 0149). It costs 40 to 100 ms more per world — `git commit` over 68 crash points took 0.63 s without it in the worlds and 4.56 s with it (`DESIGN.md`, the bullet on cost). **Refused on macOS** as `platform_unsupported`, whatever the path names (macOS has no strace, and the engine reads strace's account and nothing else); the refusal names `--oracle-fs-usage` and `--allow-unverified` under explore and replay, and says to drop the flag under preflight, which takes neither (#702). A FAIL's `replay` line carries the `--oracle` its run was given, so a FAIL whose target crossed a process boundary replays from that line — the replay's own recording needs the witness — and a replay that no longer fails is judged with it, as the exploration was (#894). `--oracle-fs-usage` is not carried: it refuses every process boundary, so its FAIL replays without a witness.
- `--no-oracle` — no oracle, not even a strace found on `PATH`. On Linux, when no flag names an oracle and `--allow-unverified` is not given, a strace on `PATH` is the oracle: it is looked for before the setup runs and not again, tried on this binary with the trace classes the recording asks for, and attached only when that try exits 0 within ten seconds. One that cannot trace here — ptrace denied, a strace too old for the classes — is left out, and a would-be PASS is refused `completeness_not_verified` with strace's first complaint in the message. Once tried and attached, the report says the witness was found, and `oracle_witness` is `"strace"` as for `--oracle`; a run stopped before the try reports no oracle (#950, ADR 0141). `--allow-unverified` alone attaches nothing, `sideeye mcp` passes this flag unless `SIDEEYE_MCP_ORACLE` names a witness, and `sideeye demo` passes it. Exclusive with `--oracle` and `--oracle-fs-usage`.
- `--oracle-fs-usage` — the macOS oracle, in place of `--oracle`. It compares the recording run against `fs_usage`, which needs root, so `sudo` must already hold credentials (`sudo -v` first, in the same terminal — the cache is per-terminal); the run refuses rather than prompting. It is narrower than strace. `fs_usage` prints only a rename's old path and cuts long pathnames from the left (both measured), so a rename it cannot match and a state directory deep enough to be cut are refusals rather than agreements. It cannot account for other processes, so a child the shim saw, or the subject replacing its own image, is UNKNOWN under it. A single-process run with neither, whose state-directory writes come from one thread the shim recorded — the main thread or a worker — is explored and judged under it as under `--oracle` (ADR 0060), however `--work` is spelled — through a symlink such as the default `/tmp/sideeye-work`, or relative — and whether the target writes through `/tmp`, `/var` (where `$TMPDIR` lies) or `/etc` (#795, ADR 0128), and so is one that writes its standard output and standard error, or moves a file onto a standard descriptor with `dup` or `dup2` and writes through it, as GNU `dd of=` does (#796, ADR 0122): the engine tells the reader where descriptors 0, 1 and 2 point — 0 and 1 it set up, 2 is its own stderr — since the capture cannot, and `fs_usage` runs without a class filter, which is what prints `dup` and `dup2` with both numbers. The rest: [What `--oracle-fs-usage` refuses](#what---oracle-fs-usage-refuses).
- `--allow-unverified` — accept a PASS with no completeness check. On macOS this is the answer when no privilege is available: SIP leaves DTrace's syscall provider with no probes even as root, and the one candidate that measured oracle-shaped, `fs_usage`, requires it. The report says which claim was made, and this one is weaker.
- `--world-timeout <s>` — a wall-clock budget per explored world (1 to 86400, off by default), strace's time included under `--oracle` — where the engine cannot make cgroups, a world whose child left the process group holds strace, and the world, until that child exits. A world's operation still running when the budget expires is sent `SIGKILL` and refused UNKNOWN `child_timed_out`, with the budget in the message. Worlds only: a recording run, a setup command or a checker that hangs still hangs, so this is not a promise of a hang-free run. Setting it also resets `SIGCHLD` to its default disposition for the whole run, and it is not settable over MCP today.
- `--interleave` (explore) — **at each crash point the operation is paused instead of killed, a second copy of the same operation runs to its end, the first is resumed, and the world FAILs when the state both leave differs from running the copies that succeeded one after the other (or neither succeeded, or the checker fails).** The report's `crash_model` is `"interleave"`. Linux, the default observation mode, a process that creates no other process, and `--world-timeout` only; the rest: [What an interleaved run judges](#what-an-interleaved-run-judges).
- `--power-loss rename-before-data` (explore, Linux) — judge one rule of power loss as well as the process kill (#960, ADR 0147). With `--power-loss rename-before-data` and `--oracle` (Linux), explore also judges, at each crash point and after the operation, the world in which each file the run wrote and renamed into the judged state — with no `fsync` or `fdatasync` recorded for it anywhere in the run, nor for its new name after the rename, and its new name changed by nothing else before that point — holds only what it held before the run, or nothing; a world that fails is a FAIL whose report and case name that model, and `sideeye replay` rebuilds it. A run in which a sync Sideeye does not record is seen judges no such world, and a file whose truncation strace and the shim's record cannot be matched on is not judged; the report says both. Without the flag, no verdict changes. What the file held before the run is its content in the state the operation started from, when the run neither truncated it (an `O_TRUNC` open, which strace reports, or a `truncate`) nor removed, replaced or linked over it, nor renamed it or a directory above it away; otherwise it is empty. A source that is a symbolic link is left out. The calls that stop it — strace sees them, the shim does not record them as syncs — are `sync`, `syncfs`, `sync_file_range`, `msync`, `io_submit`, `io_uring_setup`, `io_uring_enter`, an `O_SYNC` or `O_DSYNC` open that can write, a `pwritev2` with `RWF_DSYNC` or `RWF_SYNC`, and an `FS_IOC_FIEMAP` asking `FIEMAP_FLAG_SYNC`; the flag adds `sync`, `msync`, `io_submit` and the two `io_uring` calls to what strace traces, and the report's `power loss` line names each one seen, with its file. Whether an open truncated is read from strace and matched with the shim's record of that file's opens in order; a file whose opens do not match is left unjudged rather than given what it held before, and the line counts it. Needs strace as the witness — `--oracle <strace>`, or a strace found on `PATH` that can trace here — and refuses `--no-oracle`, `--allow-unverified`, a recovery, and macOS. The text report adds a `power loss` line and, on a FAIL, counts the two kinds of world apart; the JSON report adds `power_loss_rule`, `power_loss_worlds`, `power_loss_violations` and `power_loss`, and `earliest.crash_model` names the rule when the earliest world is a power-loss one. Such a FAIL's case is version 9 and names the rule, its `reproduce` line is the replay, and `sideeye replay` takes the rule from it — the flag itself is refused there — and needs strace as the witness too. Off by default because whether the rule holds depends on the filesystem.
- `--stop-when-orphaned` — stop at the next world boundary if the process that launched the run exits (UNKNOWN, `parent_exited`). The MCP server passes it on every explore and replay: agent hosts restart MCP servers routinely, and an orphaned exploration otherwise keeps killing processes and rewriting its state directory with nobody left to report to. A run that hangs before a boundary is out of reach, unless the server itself is stopped by a signal it can catch: it hands that signal to the engine (next item).
- **Stopped by a signal, a run stops what it is running first** (#819, ADR 0124). `sideeye explore`, `replay` and `preflight` — `demo` runs one of them — and `sideeye mcp`, stopped by SIGINT, SIGTERM, SIGHUP or SIGPIPE (Ctrl-C, a cancelled CI job, a closed terminal), stop the child they are waiting on — a setup, the operation and strace with it, a checker, a recovery — the way a world over `--world-timeout` is stopped: `SIGKILL` to its process group, and everything in the cgroup the engine made for it where it made one; `fs_usage` is stopped as at the end of a recording. The MCP server hands the signal to the engine it is waiting on, which does the same. Then the process ends by the signal it received, with a line on stderr naming it; a run stopped before its verdict writes no report and prints no `json sha256=` line. The rest: [When a signal cannot end the run's child](#when-a-signal-cannot-end-the-runs-child).
- `--state-under <dir>` (explore, replay and preflight) — the directory the state must resolve strictly inside; anything else is refused before setup runs. A case file names its own state directory, and a config its own, and all three commands empty and rebuild it — explore and replay before the recording run and every world, preflight before its run or each of `--twice`'s two — so this is how a caller that vetted only the file's path bounds where it may point the deletion. The MCP server passes its `SIDEEYE_MCP_STATE_ROOT` (default: the server root) on every exploration (#765), every replay and every preflight (#717, #815).

## The entries above, in full

The rest of the longer entries in the two lists above, each under a heading of its own; every entry links to its part.

### What the start check leaves unjudged

Not judged, and still arriving as whatever status the failed exec leaves: a bare name when `PATH` is unset (the libcs' default lists differ), a script this user can execute but not read, a `#!` line longer than 256 bytes, a relative interpreter, an `env` line with a flag, a second word, or a name holding `/` or `=`, a second level of `env` (the file `env` finds has a broken `#!` of its own), an executable whose dynamic loader is missing (a glibc binary on Alpine), an image built for another CPU, and a file that disappears between the question and the spawn. Under `--observe supervised` and `--oracle` the operation is launched from the first file of that name on `PATH` with no fallback, so a broken first file with a working one behind it passes the question and fails at the spawn. The `[recovery]` commands are not asked about — a recovery changes no verdict and no exit code, so one that cannot start shows as `recovery.result` `unknown` (#701, ADR 0092).

### What an interleaved run judges

`--interleave` asks whether two copies of one operation, run at once, leave the state they would leave run one after the other — the question a missing lock or a lost update fails (ADR 0148). It is a separate exploration with a separate failure, not added to the kill: a run takes one or the other, and its `not_tested` names the other.

The yardstick is two states the run builds first: the state one run leaves (the baseline world, the shim loaded and nothing armed), and the state two runs in a row leave, built twice without the shim and refused UNKNOWN `baseline_violates_invariant` when the two tries differ (a target that writes the time or unpinned randomness ends here). An operation that does not succeed the second time it runs, an `init` that refuses an existing state, is refused as a setup error. Then, for each crash point *k*, the shim stops the operation at the thread about to perform the *k*-th state-changing call, before that call, and the engine starts the second copy without the shim and waits up to 5 seconds; it then resumes the first whether or not the second has ended, so a second copy blocked on the first's lock proceeds once the lock is released, and both must end within `--world-timeout`. When both copies exited the expected status, the state must equal two runs in a row; when one did, one run; when neither did, the world fails. The comparison skips declared `scratch` paths, and the checker runs on every world as it does under a kill. The report's `interleave` field counts the worlds whose second copy ran past the wait and those whose second copy did not succeed; the text report's `interleave` line says the same.

What it does not do. Only one pause, at a crash point of the first copy: three or more copies, a pause inside the second copy and a different second operation are not explored. The second copy's own operations are not recorded, so what it does is judged through the final state and the checker alone. A target blocked in a system call when it is resumed may see it return `EINTR`, as after a terminal's Ctrl-Z, and the verdict is about the path it then takes. A target that waits on a lock spends up to 5 seconds at every crash point, and `--world-timeout` must be longer than that wait. Refused as setup errors: macOS (a stop sent at the calling thread is not delivered there), `--observe syscalls` and `supervised`, `pin:random` (the second copy would draw the first copy's numbers, or none), a success marker (it is about one run's output, and a world has two), a declared recovery, `--leave-crash-state`, a run without `--world-timeout` or with one not longer than the wait, and a recording that created another process (a pause would leave it running beside the second copy). A FAIL saves a version-9 case carrying the wait; its replay builds both yardstick states again and runs that one world, and needs `--world-timeout` as the run did — so over MCP, where that flag cannot be set today, such a replay is refused.

### Where the commands run

For a define read from a toml that declares no `cwd`, run from a directory other than the toml's, a refusal also says what it saw when the command that failed carries an argument present under the toml's directory and absent where it ran — or, for a file it is about to create, a directory above that file that is — `./state is under the toml's directory /proj and not under /home/u, where the commands ran` — and names `cwd = "."` as the line to add: in `next_step` on `recording_run_failed` (an exit status nobody declared, or no normal exit), `marker_never_observed`, `nothing_could_fail` when there was no crash point (an operation that found nothing to do where it ran), `checker_not_falsified` when the checker accepted the corrupted state, `checker_rejects_initial_state` when it rejected the state the define starts from, and `baseline_violates_invariant`'s checker layer; in the sentence itself on `setup_failed` when the setup exited non-zero, and wherever `--observe syscalls` keeps its own step (#700, ADR 0093). Not asked for a config read through a link or a pipe (`/dev/stdin`). It sees nothing when the command finds a different file where it ran and succeeds, or writes outside the state directory through an argument that names nothing either side — which is why the README's toml example declares `cwd = "."`. In a `sideeye.toml` a relative `cwd` resolves against **the toml's own directory**, not against where Sideeye was started and not against the project's root unless the toml sits there; given as the `--cwd` flag it resolves, like any path on the command line, against the directory Sideeye was started in. **It is resolved and checked before the state directory is made**, so that a define naming a directory that is not there refuses before anything on disk has moved — which means **a `cwd` that only your own `setup` creates is not there yet when it is checked**: the run refuses as a SETUP ERROR (`the declared cwd could not be resolved`) before setup runs. (Left over from an earlier run it would resolve, which is worse — the define would work on one machine and not on a clean one.) Build such a directory before Sideeye starts — in CI, in the step before the one that runs it.

### What a recovery is held to

Where the engine can make cgroups (Linux, as for a world), each recovery command and check runs in one of its own and everything it started is stopped when it exits — so a daemon the recovery starts does not reach the next leg, a check that needs that daemon running cannot be judged this way, and a recovery that hands the rest of its repair to a process it leaves is cut short there — the `recovery` line says how many processes each command left. Five limits come with it. The rebuilt state carries the crash's permission bits (since #678, ADR 0109) but restore-time timestamps and the engine's ownership, so a recovery that decides by modification time (make, ninja) sees every file as newly written — a `pass` from such a tool can be manufactured by that — and two names of one file come back as two files (ADR 0006). Only the saved exhibits are recovered, and the `recovery` line says how many of the run's failing worlds that was. The state directory afterwards holds what the last recovery left, not the baseline's result. Where the engine cannot make cgroups (macOS, or a Linux host without one to make), only the command's process group is stopped: a process that left the group, and anything a recovery writes outside the state directory anywhere, survives into the next leg — the next exhibit or the completed-state control — and can change what that leg reports. And the crash snapshots of the saved exhibits are held in memory until the exploration ends, so a run near the machine's memory can stop at a later world's snapshot where it would not have without a recovery. And a recovery that never ends holds the run the way a checker does unless `--world-timeout` bounds it. Both keys take the string form only: on a replay the same two commands travel as flags — accepted there, unlike the rest of the define, and printed on the replay line single-quoted — and a flag has no argv form (ADR 0072).

### The work directory

`--work` moves the scratch directory for traces and cases (default `/tmp/sideeye-work`). **A relative `--work`, `--shim` or `--oracle` is read against the directory Sideeye was started in, for every run and every process in it** (#895): a target that changes directory before it runs another program — `cd "$SIDEEYE_STATE_DIR" && exec tool` — is traced in the explored worlds, and in preflight's second run, as it was in the recording, and the paths the report prints from them (`case`, `replay`, `evidence`, `reproduce`, preflight's `next`) are absolute. It used to be pinned only under a declared `cwd`, and such a target lost its account in every world and was refused as though it had broken its own exec chain. Two spellings are left as given when no `cwd` is declared: a `--shim` or `--oracle` with no `/` in it, which the loader or `PATH` looks up rather than a directory, and a `--shim` whose absolute path would hold a space, a tab or a colon, which `LD_PRELOAD` splits on (`DYLD_INSERT_LIBRARIES` on the colon) — a target that changes directory then loses that shim, as before. When the starting directory cannot be read, a relative `--work`, or a `--shim` or `--oracle` that would be read against it, is refused as a SETUP ERROR before setup runs and before the state or work directory is made. **It has to be yours** (#692, ADR 0099): the cases saved there are commands a replay runs, so a work directory Sideeye did not just create is refused before setup runs when its last component is a symlink (yours or not), when it is not a directory, when its name ends in `..`, when another user owns it — root included, unless you are root — or when its kind or owner cannot be read; the refusal names the directory and why, and Sideeye writes nothing under it (a `--json` report you point there is still written, as every refusal's is). A name that cannot be resolved at all is refused as before, naming the error. The way past is a name that does not exist yet, which Sideeye creates as yours, or a directory of your own. What used to run and now refuses: a link of your own at the name — pass the directory it points to — another user on the same host who made `/tmp/sideeye-work` first, `sudo sideeye` pointed at a directory you made, and a root container handed a bind mount your host user made. This too is a mitigation, not a boundary: it inspects the name once, and anyone who can write the directory's parent can swap it afterwards.

### The trace file

**A symlink at the trace path is refused rather than followed — by every process the shim is loaded into when it writes the trace (#488), and by the engine when it reads that trace back (#489).** The engine removes the file before each run, but every process the shim reaches opens the name again afterwards and the later ones have nothing standing in front of them, so without the write-side refusal a link planted there would append the run's records to whatever it points at; without the read-side one, the account the verdict is drawn from would be whatever that link pointed at. A **FIFO** appearing at that path after the engine's own removal of it is refused on both sides as well: the read takes regular files only (#400), and the write does two things that answer different cases (#492): it opens **non-blocking**, so a FIFO with no reader fails outright instead of waiting for one — this is the half that stops the wait, in a constructor that runs before the target's `main`, inside a recording run with nothing to time it out — and it then asks what the descriptor turned out to be, closing it unless it is an ordinary file, which is the half that catches a FIFO somebody is already reading, along with a device or a socket. The one thing the write side leaves standing is a kind it could not read at all, a `statx` that fails: a host lacking it goes on refusing with `unresolvable_path`, which names a cause, rather than with a silence that names none. What is **not** refused: a **hard link** is the same file rather than a pointer to one, so no open flag sees it, on either side. Nor is the target on the other side of a boundary here — it holds the trace path in its own environment and can write the work directory, so a target that wants to hand Sideeye a trace it wrote itself is not something this or any flag stops.

### The JSON report's digest line

When the file is in place one line goes to stderr, in a single write: `sideeye: json sha256=<hex>;`, the digest of exactly the bytes written -- so a machine that receives the report through a directory the judged program can also write can tell the file it opens from one written after it. When the report could not be written the line reads `sideeye: json sha256=none;`. It is exactly one line per run that got as far as producing a document — a report, or `preflight`'s own (#717) — it is not part of the report schema, and a reader should count it wherever it appears rather than at a line start (a program sharing the descriptor can take the line start away, but not the token). It is the **last** thing sideeye writes, on every path -- the digest is recorded when the report lands and emitted at the exit, after the text report, so a reader that takes the first line of sideeye's output sees what it always saw — through a pipe or a file, where the verdict word is never coloured.

### Commands that look written for a shell

A toml command value with an inner `"` followed at once by `#` — `check = "grep -c "#include" f"` — is read as ending at that quote, with the rest a comment; it is accepted as it always was, and the warning says what the command became. The sentence is in the report as `warning`, in the JSON as `define_warnings`, in `sideeye mcp`'s summary, and on Sideeye's standard error as `sideeye: warning: …`, written once at the end so the first line of merged output is still the verdict — which also reaches a run that ends in a SETUP ERROR, and `preflight`. A replay is not looked at: its case holds commands an exploration already read. Left alone: a symbol inside a word (`x=n*10`, `ggiX<esc>`, `~>1.6`, `%(title)s`), a version constraint (`>=1.6`), a glob, a brace, a backslash outside quotes (`a\ b`) — each means what it says to a program run without a shell. A toml value the parser refuses as not one double-quoted string — `state = './state'`, `expected_status = 0`, `operation = "tool "two words""` — is refused with the line it would have been read as, when that line parses back as one value the writer could have meant: a trailing comment is kept, a value that reads two ways (`"a" "b"`) and one holding bytes the report would have to rewrite get no line.

### How supervised mode counts, and what it refuses

**A statically linked target, which the other two modes refuse as `no_shim_marker`, is counted and reaches a verdict under this mode**, with the oracle watching the same run (one that starts a dynamic child, which those modes let past their gate because the child carries the shim, is sent here by three refusals in the shapes measured to be crossed, [report-schema](report-schema.md), #685; its other refusals keep their steps); a dynamically linked target is sent here when a process it ran closed the shim's trace, as a program does when it closes every descriptor before it starts another (#988); where it cannot be judged it refuses with an existing reason. Each state-changing call waits for the engine, which counts it and lets it run, or at the crash point kills the run while the call is still waiting, so the call never runs. Where the engine can make a cgroup, the crash point's kill reaches every process of the run through it, however one left the process group. Where it cannot — `docker run`'s defaults, a GitHub-hosted runner's steps — the run is held by its process group, as the other modes hold a run without one: the kill reaches the group, the caller and the subject, and a process that leaves the group (`setsid`, `setpgid`, which the filter traps) refuses `child_process_detected`; the engine does not stop that process after refusing, a writer still running when the direct child exits is killed without being named, and on x86_64 an i386-compat or x32 `setsid` or `setpgid`, which the filter does not see, escapes the kill unrecorded. Measured in Docker Desktop's default container in [target-classes](target-classes.md) (ADR 0089, decision 4 as amended). Its walls: a run whose writes come from two or more threads refuses `multiple_threads_detected` — writes under scratch and a `mkdir` of a directory the state started with aside (ADR 0139) — because the thread-order records are the shim's — and recording thread creations and exits from outside instead is not built: of 50 recording runs this mode refused for jj, OpenTofu, codex and doctl, 48 hold a hand-over between writing threads that neither a thread's creation nor its exit orders, and doctl's other two were ordered by a creation the Go scheduler happened to make (#687, `spike/dogfood/2026-10-10-thread-order/`; tombi, refused in 1 of 36 supervised explores and 3 of 20 replays while its preflight was accepted 26 times of 26, was not read); a target that installs its own seccomp filter can return an error or trap for a call before this one sees it; `no_new_privs` is set, so a setuid child does not gain its privilege; i386-compat and x32 calls are not seen. Reading a call's paths needs the engine to read the target's memory, which Yama's `ptrace_scope` governs: at 2 or 3 every in-scope operation is unplaceable and the run refuses rather than guesses. The filter outlives the engine only as long as the engine does: were the engine to die mid-run, the target's next watched call would fail with `ENOSYS` — a changed target, which the run that follows cannot report because nobody is left to report it. On a run that reached the oracle comparison — whether it agreed or refused — and under `--allow-unverified`, the report's `oracle` line says who counted: the supervising engine, from outside the target, with no shim loaded. A run refused before the comparison (a thread refusal, say) says `not compared`, as in every mode.

### A case replays under its own mode

**A case saved under `--observe syscalls` or `--observe supervised` records the mode, and is replayed under it with no `--observe` given** — by `sideeye replay <case>` and by `sideeye_replay_case` over MCP alike (#691, ADR 0100). The report's `replay` line still names the mode, which a replay accepts when it matches; an `--observe` naming another mode is refused by name, because the case's crash point is a number in its own mode's count. Such a case is `case_version` 6 — or 7, when its define also declares an `apparatus` entry a replay checks (ADR 0136) — which a binary before this change refuses as unparseable rather than replays; a case counted under the default keeps the version its define asks for — and when that is version 7, a define with an `apparatus` entry a replay checks, the case spells the mode whatever it is, `wrappers` included, so an `--observe` naming another mode is refused on it as well (ADR 0136). A case saved before this change records nothing, and is replayed under the flag, or the default, as it always was.

### What `--oracle-fs-usage` refuses

A descriptor the reader cannot place still refuses: a pipe the target makes itself, or a `socketpair` it writes before any socket call names it, for which `fs_usage` prints no number, or a number moved from one the capture never saw opened. A run in which `fs_usage` reports a buffer overrun on its stderr, or whose stderr cannot be read back, refuses, since a dropped event is an operation neither account holds. **Two limits are Sideeye's and fixed in this build** (#896, ADR 0031): `fs_usage` is given 1800 seconds, and the reader holds at most 2 GiB of its capture, which records the whole machine and is written to `--work` for as long as the recording runs — a recording that outlasts either is refused `oracle_saw_nothing` naming the limit and what it measured, not the environment. Before, the time limit was 90 seconds and the refusal blamed the environment. If the engine dies without stopping `fs_usage` — SIGKILL, a crash — a process it started beside the observer stops it within seconds; the 1800 seconds bound it only if that process is gone too, or after a stop the engine reported as failed (`fs_usage did not stop when asked`), when the engine has let that process go. Stopping `fs_usage` at the end of a recording uses the same `sudo` credentials: if they expired during the recording, it is sent SIGTERM instead, and a capture that loses its end to that is refused `oracle_saw_nothing` rather than judged.

### When a signal cannot end the run's child

When the child it waits on is one that signal cannot end — in an uninterruptible wait, or under credentials it switched to — that child's group is named on the line after 5 seconds (20 for the engine `sideeye mcp` waits on, which has its own child and `fs_usage` to stop first) and left running; a second signal ends the run at once, with `fs_usage` sent the SIGTERM that stops it but not waited for. What it does not do: a process that left the child's group is stopped only where there is a cgroup, and one further down that the signal cannot reach — under sudo, say — survives unnamed, both as under `--world-timeout`; a signal ignored when Sideeye started (`nohup`) stays ignored, and the children it starts inherit that; the state directory holds what the stopped child left, not the state from before the run; and SIGKILL, which no process can catch, still leaves the run's children running.

## Example

Real output — the same planted delete-before-rename bug the demo uses (`spike/toys/toy.c`), explored with a checker and the strace oracle; the paths are the container's, and the engine hands the target its state directory via `SIDEEYE_STATE_DIR` and, for the toy, `TOY_STATE`:

$ TOY=/tmp/se/toy-bug /work/zig-out/bin/sideeye explore --state /tmp/se/state \
    --setup "/tmp/se/toy-bug init" --operation "/tmp/se/toy-bug rotate" \
    --check /work/spike/check.sh --shim /work/zig-out/lib/libsideeye_shim.so \
    --work /tmp/se/work --oracle /usr/bin/strace

falsify: doctor says 'healthy' but the key is unloadable
world 5: doctor says 'healthy' but the key is unloadable
FAIL  1 of 6 explored worlds violated an invariant

invariant   built-in atomicity, and the checker
earliest    crash point 5 of 5
            after  unlink(/tmp/se/state/key.json)
            before rename(/tmp/se/state/key.json.tmp)
path        key.json
observed    present before and after the operation, but gone from the crashed state
cwd         /work  (none declared: Sideeye's own)

explored    6 worlds (crash points 5 + 1 baseline)
expected    exit 0
atomicity   1 path(s) judged pre-or-post
oracle      agreed on 5 operations (88 syscall lines examined, 12 in scope of the judged state), witness strace; and agreed in each of 6 explored world(s)
metadata    none observed. Restore reproduces permission bits (read, write and execute; a directory's owner bits are added) but not ownership, set-id or sticky bits, extended attributes or timestamps: crash worlds start from the recorded permission bits, with timestamps assigned during restore
syncs       1 rename(s) into the judged state. Each file with a write recorded was synced (fsync or fdatasync) after its last recorded write and before its rename. An account, not a verdict: a process crash keeps unsynced writes, and power loss is not tested.

Read the account block, not just the verdict: `explored` says how much was looked at, `oracle` says a second witness (strace) checked the shim's account against the kernel's, `checker` says the invariant was proven able to fail before the run began, `cwd` says where the define's commands ran — Sideeye's own directory here, because this define declared none — and `not tested` names what this verdict is silent about. A PASS and an UNKNOWN print the lines they share with this block under the same keys, in the same columns and the same order — `cwd`, `apparatus`, `warning` and `recovery` first, then a blank line, then the rest — and each verdict prints a fixed set: a PASS has no `replay` or `evidence`, which belong to a counterexample, and an UNKNOWN leaves out `explored`, `oracle`, `metadata`, `syncs` and `checker`, because a refusal can be raised before the exploration and would print figures for crash points it never reached (the JSON report carries all of them on every verdict but `syncs`, which it leaves out of a refusal too). On an explore's FAIL that saved its case, `replay`, `evidence` and `reproduce` are commands that run as printed (#709, #711). `replay` and `evidence` run with `sideeye` on `PATH` — `replay` from the directory the `cwd` line names when the define declared none, since an undeclared define's commands run where Sideeye is started, and with the `--observe` mode the run used, which a replay also takes from the case itself when the mode is not the default. `reproduce` runs in a POSIX shell once the define's setup has left the state it starts from — as often as it is pasted: in a subshell, it changes to the directory the commands ran in, empties its trace file (the shim numbers on from the highest number a trace already holds, so a second paste into a full one would never reach the crash point), sets the variables Sideeye hands a world — except that a pasted line runs in neither a world's process group nor its cgroup, so it unsets `SIDEEYE_KILL_GROUP`, whose mere presence would take the reader's own shell down with the target, and pins the cgroup ones empty; and it does not carry `TOY_STATE`, the demo toy's own name for the state directory, which the toy reads `SIDEEYE_STATE_DIR` for when it is unset — and runs the operation's own argv with standard input from `/dev/null`, as every command Sideeye runs has it. Its standard output is the terminal, where a world's was a file. **A `SIDEEYE_KILL_AT` or `SIDEEYE_KILL_GROUP` left exported in your shell no longer stops any run** (#822, ADR 0126): Sideeye removes both from its own environment when it starts, and only a world, armed by Sideeye at its own crash point, carries them; `SIDEEYE_MCP_CHILD_ENV` refuses to name either. The line starts from the state the setup left, not the rebuilt one the recording and every world start from (#815), so a target that reads what the rebuild changes — the order tmpfs, btrfs or XFS list a directory in, an owner, a timestamp — can meet another operation at that number; `replay` starts from the rebuilt state. It dies in front of the same crash point, in the process that reaches it: where the run admitted writing children, the rest of the tree keeps running, so the state can go further than the report's. Every value is quoted where a shell would read it otherwise, and a bare first word is quoted too, so an alias of that name in an interactive shell is not what runs. The line keeps the placeholder `<operation>`, with no `cd`, when the operation or its directory holds a byte the report defangs (rather than print the byte, or a defanged command that names something else), when Sideeye could not name the directory, or when the command would not fit the text report's output buffer. A replay's own FAIL prints the sentence it always did on `replay` and `-` on `evidence`; a FAIL whose case could not be written, `-` on both; under `--observe supervised`, `reproduce` names the replay line, the one command that reproduces a crash point counted from outside the target.

The `check` script is where your invariants live. This one cross-examines the tool's own diagnostic — a tool is allowed to be broken as long as it says so; the violation is the claim and the observable truth disagreeing:

```sh
#!/bin/sh
claim=$("$TOY" doctor 2>/dev/null) || claim="unhealthy"
"$TOY" load-key >/dev/null 2>&1 && reality="loadable" || reality="unloadable"

case "$claim:$reality" in
    healthy:loadable | unhealthy:unloadable) exit 0 ;;
    *) echo "doctor says '$claim' but the key is $reality" >&2; exit 1 ;;
esac
```

The full version is [`spike/check.sh`](../spike/check.sh). Sideeye refuses to trust a checker it has not seen fail: before exploring, it corrupts the state and requires the check to reject it. A checker that cannot fail makes the run UNKNOWN, not PASS. More worked checkers: [docs/checker-cookbook.md](checker-cookbook.md).

## What it is for after the first find

The finding is not the durable artifact — the declaration is. A `sideeye.toml` and its checker are the question, not the answer, so re-asking it after the tool changes is `explore --config` again, and the report says what it looked at that time rather than assuming the last run still holds. A saved case is deliberately narrower: it names one crash point in one recording, and when the recording moves underneath it the answer is `case no longer applies` rather than a silent pass — which is what makes a case worth keeping in CI. This repository keeps its own oldest finding that way, re-recorded under the current trace contract on every push to main and every pull request (the `timew-regression` job in `.github/workflows/ci.yml`). And because a target Sideeye cannot fully observe is UNKNOWN and never exit 0, a machine caller can tell *checked and clean* from *not checked*, which is the distinction an unattended run has to get right. What none of that does is constrain what your declared operation may do — that boundary is the config you vet, as [the MCP page](mcp.md) says.
