# The CLI in full

The README carries the shortest path to a first verdict. This page carries the rest: the platforms it runs on, installing without Homebrew, every flag and what it refuses, what a saved case is and how replay reads it, a full report with the checker that produced it, and what the declaration is for once the first finding is in.

## Installing without Homebrew

Take the tarball for your platform from [Releases](https://github.com/yottayoshida/sideeye/releases). Sideeye ships as a binary **and** a shim library, and it looks for the shim beside **itself** — the binary's own canonical path, never the working directory — before `../lib`, so an untarred release runs from anywhere and needs no `--shim` unless you have separated the two files. That search declines a candidate it cannot attribute (a symlink, or a file someone else owns), so an install directory that is not yours alone is refused by name rather than trusted:

```
$ tar xzf sideeye-v1.10.0-aarch64-macos.tar.gz && cd sideeye-v1.10.0-aarch64-macos
$ ./sideeye version
```

Each release asset carries a sha256 GitHub computed when it was uploaded, so checking a download needs nothing published beside it (on Linux, `sha256sum` in place of `shasum -a 256`):

```
$ gh api repos/yottayoshida/sideeye/releases/tags/v1.10.0 --jq '.assets[] | "\(.digest)  \(.name)"'
$ shasum -a 256 sideeye-v1.10.0-aarch64-macos.tar.gz
```

The digest reads `sha256:<hex>`; compare the hex. What this establishes is that the bytes are the ones GitHub holds — not who produced them: the digest and the release are the same account's word, and a checksum file published in the same release would be too.

Or build from source with Zig 0.16.0: `zig build` — binaries land in `zig-out/bin` and `zig-out/lib`, which is the same shape.

## Usage

Three commands, in the order you will meet them.

**1. See it work** — sixty seconds, nothing to install beyond Sideeye itself:

```
$ sideeye demo
```

The demo writes a small planted-bug tool into a new directory under `$TMPDIR` (or `/tmp`), explores it, and prints a real FAIL report. The tool is built into the binary, so no compiler is needed (#715). The directory is named on the demo's first line and left in place, so the case it saves can be replayed; delete it when you are done. Exit 1 — the planted bug found — is success, which makes the demo double as a smoke test of the binary + shim pair.

**2. Ask whether Sideeye can watch your tool** — before writing any config, and again once you have one:

```
$ sideeye preflight --state <dir> --operation "<cmd>"
```

One observed run: either `recording accepted` (exit 0) or a refusal naming the same detector a real run would use (exit 2). An accepted run — under `--twice`, one whose two runs left the same bytes — ends with a `next` line, the `explore` command for the define it just accepted, ending in what explore on this platform takes: the second witness `--oracle <strace>` on Linux; on macOS, where `--oracle` is refused, `--allow-unverified` — no second witness, the weaker claim, said so in the report — with `--oracle-fs-usage` named in the note above it as the witness macOS has (#702).

Once a `sideeye.toml` exists, the same question takes the toml itself, read as explore reads it:

```
$ sideeye preflight --config sideeye.toml
```

**Every define mistake listed below is refused by `sideeye preflight --config` before any crash world, by the same detector and in the same words `explore --config` uses** — one mistake per run, the first one met, as explore does (#704, ADR 0094):

- the toml does not parse: a syntax error, an unknown key, a value of the wrong shape;
- a `cwd`, `apparatus` or `scratch` entry that does not hold;
- a `state` that is not a directory;
- a `setup`, `operation` or `check` that cannot be started, as the Usage list below defines it;
- a `marker` the recording run does not print (`marker_never_observed`);
- an operation that changes nothing in the state directory, so there is no crash point (`nothing_could_fail`) — explore answers this in the same words when it is given `--oracle` or `--allow-unverified`, and answers the completeness gate first without either;
- for an operation with a crash point, a `check` with no command in it (`--check is empty`), or one declared against a state with nothing in it to corrupt (`checker_not_falsified`);
- in a toml with no `cwd`, run from another directory, a relative argument that is under the toml's directory and not where the commands ran — named, with `cwd = "."` as the line to add.

Neither the check nor a `[recovery]` is run: the report says each was declared, and a recovery that cannot be started moves no verdict in explore either (ADR 0072). What a world can do differently from the recording is not on the list: an operation that changes the state but nothing the verdict judges can still be refused `nothing_could_fail` by explore, which only a crash world shows. An accepted run's `next` line is `sideeye explore --config '<the toml>'`, named in the directory its relative paths were resolved against (a toml that is a symlink keeps its own side); a toml read from `/dev/stdin`, from a shell's `<(…)`, or through a link into `/dev` or `/proc` gets a line saying to save it to a file first, and one whose name cannot be printed as typed a line saying to copy it to a file with a plain name. (zsh's `=(…)` is an ordinary temporary file and is named as one, though it is gone once the command ends.)

Add `--twice` and it observes a second run from the restored pre-state, at least two seconds later, and compares the two. Byte repeatability is a property of two runs — one observation structurally cannot see it, and a tool that rewrites a timestamp on every run passes everything else preflight asks and is refused only once a full define has been written and explored. Equal post-states: exit 0. Different: the differing paths are named and the command exits 1, which is the negative answer to the question `--twice` asked, not a FAIL verdict — preflight produces none. Under each path it names whose content differs, up to eight of them, a `bytes` line says where the two runs' bytes first differ (a byte offset counted from 0), how long the differing stretch is in each run — what is left once the bytes both runs share at the front and at the back are taken off, widened over shared bytes to a whole UTF-8 character where the first or last difference falls inside a valid one (the line then says where the stretch starts) — what kind of bytes it holds (decimal digits; hex digits, which takes a digit and a letter both; printable text, tabs, line ends and invisible format characters included; or how many bytes fall outside printable text), and quotes both stretches, each clipped at 48 bytes, with every byte outside printable text — tabs and line ends too — and every character that reorders or hides text on a terminal (the bidi controls, the zero-width and invisible marks, tag characters) spelled `\xNN` (#688):

```
difference   nondet.txt (content differs)
             bytes first differ at byte offset 4: first run "1", second run "2" — 1 and 1 byte(s) of 10 and 10, both decimal digits
```

The quoted bytes are in preflight's text output, and — when `--oracle` ran — in the oracle's capture in the work directory, since strace prints the start of what each write wrote; they are not in its `--json` document, which carries where, how long and what kind (below). So wherever the text output or the work directory is kept, a CI log or a committed transcript, those bytes of the state are kept with it. An exploration that refuses `baseline_violates_invariant` over the same difference says where, how long and what kind, and no byte of either stretch, because its message reaches the JSON report, the MCP answer and the reports people paste upstream — and a stretch two runs disagree on is exactly where a per-run token or secret sits. Neither names a cause; [docs/apparatus.md](apparatus.md#reading-a-byte-difference) maps the common shapes to `scratch` and `apparatus`. What it does not establish is that the target is deterministic: the comparison covers file bytes, entry kinds and symlink targets in the state directory (`--state`, or a toml's `[world] state` under `--config`), and two runs are not all runs.

With `--json <path>`, preflight writes what it found as JSON (#717). A refusal or a stop is a report, `sideeye/report`, carrying the refusal the text shows — usually the one `explore` reaches on the same define, though not always (above: with no crash point and neither `--oracle` nor `--allow-unverified`, explore answers its completeness gate first). An accepted recording, or two runs that differ under `--twice`, is a document of its own, `sideeye/preflight`: the outcome, the account, the set of paths the built-in invariant judges, and under `--twice` each differing path with where, how long and what kind of bytes — never a byte of either run ([docs/report-schema.md](report-schema.md#preflights-document-preflight---json)). The exit code is the same as without the flag.

**3. Explore** — the real thing, with the whole define in one file. The first line is Linux's; the second is macOS's, where `--oracle` (strace) is refused:

```
$ sideeye explore --config sideeye.toml --oracle /usr/bin/strace
$ sideeye explore --config sideeye.toml --allow-unverified
```

```toml
[world]
state = "./state"               # the one directory your tool's state lives in

[define]
setup     = "mytool init"
operation = "mytool rotate-key" # the shim is inserted into this one, not into setup or check
check     = "./check.sh"        # exit 0 = invariant holds; runs after crash + restart
marker    = "Recorded"          # optional: the operation's own success claim
expected_status = "3"           # optional: the exit status that means "completed" (default "0")
cwd       = "./repo"            # optional: where the three commands run (default: sideeye's own cwd)
apparatus = ["env:FAKETIME=@2024-01-01 00:00:00", "preload:libfaketime"]   # optional: what the operation's environment must carry
scratch   = ["COMMIT_EDITMSG", ".hg/wcache"]   # optional: paths under state the built-in invariants leave alone

[recovery]                      # optional: the tool's own recovery, run against each saved FAIL
command   = "mytool repair"     # the string form only
check     = "./check-repaired.sh"
```

- The same define works as flags: `--state` / `--setup` / `--operation` / `--check` / `--marker` / `--expect-status` / `--cwd` / `--apparatus` (repeatable) / `--scratch` (repeatable). `operation` is **the one command the shim is inserted into**; `setup` and `check` are ordinary commands and may be scripts. What that means for a `#!` script: the kernel hands execution to the interpreter, so the insertion has to reach *that* image rather than the file you named. Whether it can is a property of the interpreter and of the machine — a statically linked one takes no insertion anywhere, and on macOS a platform binary such as `/bin/sh` may have the variable stripped before it starts — so the same define can reach a verdict on one machine and refuse with `no_shim_marker` on another. Naming an executable image directly takes the question away.
- **A setup, operation or check that cannot be started is a SETUP ERROR (exit 3), raised before it runs**, naming the command, the file and which of these it is: the file is missing, is not a regular file, may not be executed by this user (a script needs its execute bit — Sideeye runs `./check.sh`, not `sh check.sh` — or a noexec mount or an ACL denies it), or could not be examined; the `#!` interpreter that file names is one of those; or a bare name has no executable file on `PATH`. A bare name is refused only when every file of that name on `PATH` fails this way, because execvp moves on to the next one. The setup is asked about before it runs, and that refusal leaves nothing on disk; the operation and the check after the setup has run, so a setup may build or write them — but a checker the operation itself would create is refused, so write it in `setup`. Not judged, and still arriving as whatever status the failed exec leaves: a bare name when `PATH` is unset (the libcs' default lists differ), a script this user can execute but not read, a `#!` line longer than 256 bytes, a relative interpreter, an `env` line with a flag, a second word, or a name holding `/` or `=`, a second level of `env` (the file `env` finds has a broken `#!` of its own), an executable whose dynamic loader is missing (a glibc binary on Alpine), an image built for another CPU, and a file that disappears between the question and the spawn. Under `--observe supervised` and `--oracle` the operation is launched from the first file of that name on `PATH` with no fallback, so a broken first file with a working one behind it passes the question and fails at the spawn. The `[recovery]` commands are not asked about — a recovery changes no verdict and no exit code, so one that cannot start shows as `recovery.result` `unknown` (#701, ADR 0092).
- `cwd` is where setup, operation and checker run — **a tool that only works inside its own project (git, most build tools) needs one**, and without it the commands run in Sideeye's own directory. For a tool that refuses to run outside its project that is usually `recording_run_failed`, with the exit status and no cause — or `setup_failed` when `setup` needs the directory too, whose one-line text carries no `cwd` line (the JSON does). The quiet case is worse: a tool that walks up the tree to find its project, as git does, can find a *different* one above Sideeye's directory and succeed there, and nothing refuses. Every report produced after the `cwd` is resolved says which directory the commands ran in: `command_cwd` in the JSON and a `cwd` line in the text — on an UNKNOWN under `next`, in the verdict blocks, and in `preflight`'s report, whose `next` hint carries the `--cwd` it was given — with `(none declared: Sideeye's own)` when nothing was declared (#647). For a define read from a toml that declares no `cwd`, run from a directory other than the toml's, a refusal also says what it saw when the command that failed carries an argument present under the toml's directory and absent where it ran — or, for a file it is about to create, a directory above that file that is — `./state is under the toml's directory /proj and not under /home/u, where the commands ran` — and names `cwd = "."` as the line to add: in `next_step` on `recording_run_failed` (an exit status nobody declared, or no normal exit), `marker_never_observed`, `nothing_could_fail` when there was no crash point (an operation that found nothing to do where it ran), `checker_not_falsified` when the checker accepted the corrupted state, `checker_rejects_initial_state` when it rejected the state the define starts from, and `baseline_violates_invariant`'s checker layer; in the sentence itself on `setup_failed` when the setup exited non-zero, and wherever `--observe syscalls` keeps its own step (#700, ADR 0093). Not asked for a config read through a link or a pipe (`/dev/stdin`). It sees nothing when the command finds a different file where it ran and succeeds, or writes outside the state directory through an argument that names nothing either side — which is why the README's toml example declares `cwd = "."`. In a `sideeye.toml` a relative `cwd` resolves against **the toml's own directory**, not against where Sideeye was started and not against the project's root unless the toml sits there; given as the `--cwd` flag it resolves, like any path on the command line, against the directory Sideeye was started in. **It is resolved and checked before the state directory is made**, so that a define naming a directory that is not there refuses before anything on disk has moved — which means **a `cwd` that only your own `setup` creates is not there yet when it is checked**: the run refuses as a SETUP ERROR (`the declared cwd could not be resolved`) before setup runs. (Left over from an earlier run it would resolve, which is worse — the define would work on one machine and not on a clean one.) Build such a directory before Sideeye starts — in CI, in the step before the one that runs it.
- `apparatus` names the devices a deterministic run depends on — a faked clock, a pinned `os.urandom`, a stand-in compiler — so the define is the whole question and the report says what it ran under. Sideeye applies none of it; after `setup` it checks that each `env:`, `preload:` (a line of `/etc/ld.so.preload`) and `pythonpath:` entry is present in the environment the operation inherits and refuses the run as SETUP ERROR when one is not. `note:` entries are carried unchecked. Recipes and the one thing to know about global preloads: [docs/apparatus.md](apparatus.md).
- `scratch` names the paths under `state` that nobody depends on — git's `COMMIT_EDITMSG`, a tool's own cache — each entry covering the path itself and everything beneath it. The built-in invariants judge none of them, in no world: not their bytes, not their presence, whether the recording had them before, after, or both, so a torn scratch file no longer decides the verdict and a scratch file whose bytes differ between two clean runs no longer refuses the run. The price is paid in the open: the report carries the declaration verbatim, its `atomicity` line says how many recorded paths the declaration matched, `not tested` names it, and the saved case carries it (a define that declared everything reads `0 path(s) judged pre-or-post` — and, with no checker to judge the worlds instead (a marker has nothing to judge there either), is refused `nothing_could_fail`, because no world in it could have failed (ADR 0091)). What scratch does not silence: a state that changed with no operation recorded, a child the engine could not account for, an entry kind or a file size the snapshot refuses, a tree still being written when it is sampled twice — those are about what the engine observed, not about what is durable. And a checker is still the only thing that says the state is *correct*; scratch only stops the built-in layers from saying it is not (ADR 0043).
- `[recovery]` (or `--recovery` with `--recovery-check`) asks a second question about each FAIL: what does the tool's own recovery do to the state the crash left? **Declaring a recovery changes no verdict and no exit code; for each saved FAIL world it adds what the tool's own recovery did when handed that world's crash state — its names, kinds and contents, not its timestamps or permissions.** After the exploration has decided its verdict, and only when there is a FAIL, the recovery checker is first shown a state whose every file holds distinct junk and must reject it, and then the completed, uncrashed state with `command` run on it, and must accept what that leaves; then, for the earliest exhibit and the checker exhibit (once if they are one world), the crash state is rebuilt in `state`, `command` runs, the state is sampled twice to see it has stopped changing, and `check` judges it. The report's `earliest.recovery` and `checker_earliest.recovery` say `pass`, `fail` or `unknown` with the time taken, the `recovery` line says what the result rests on, and the evidence bundle carries the result. `fail` means the recovery ran, ended and was rejected; a recovery that could not be started, exited 125, 126 or 127 (the codes the engine's own child uses before exec), overran `--world-timeout`, left something still writing or running where its cgroup could not stop it, or whose checker accepted the junk or rejected the completed state is `unknown`, never `fail`. Where the engine can make cgroups (Linux, as for a world), each recovery command and check runs in one of its own and everything it started is stopped when it exits — so a daemon the recovery starts does not reach the next leg, a check that needs that daemon running cannot be judged this way, and a recovery that hands the rest of its repair to a process it leaves is cut short there — the `recovery` line says how many processes each command left. Five limits come with it. The rebuilt state carries restore-time timestamps and the engine's fixed permissions, so a recovery that decides by modification time (make, ninja) or by permission (an ssh key) sees every file as newly written — a `pass` from such a tool can be manufactured by that — and two names of one file come back as two files (ADR 0006). Only the saved exhibits are recovered, and the `recovery` line says how many of the run's failing worlds that was. The state directory afterwards holds what the last recovery left, not the baseline's result. Where the engine cannot make cgroups (macOS, or a Linux host without one to make), only the command's process group is stopped: a process that left the group, and anything a recovery writes outside the state directory anywhere, survives into the next leg — the next exhibit or the completed-state control — and can change what that leg reports. And the crash snapshots of the saved exhibits are held in memory until the exploration ends, so a run near the machine's memory can stop at a later world's snapshot where it would not have without a recovery. And a recovery that never ends holds the run the way a checker does unless `--world-timeout` bounds it. Both keys take the string form only: on a replay the same two commands travel as flags — accepted there, unlike the rest of the define, and printed on the replay line single-quoted — and a flag has no argv form (ADR 0072).
- Every define command — setup, operation, check, and a recovery's command and check — finds the state directory in `SIDEEYE_STATE_DIR`: the absolute path of `state`, resolved through any symlink, so a checker reads `"$SIDEEYE_STATE_DIR/…"` rather than a path relative to itself. `TOY_STATE`, the name the demo toy reads, carries the same path to every command, so a checker already written against it runs unchanged (#708).
- Every command Sideeye runs — your setup, operation and checker among them — starts with its standard input at end-of-file, on the CLI and MCP paths alike. A target that reads stdin sees EOF, never the terminal or pipe Sideeye itself was started from: that input is the caller's, not the define's, and a committed define has to mean the same run everywhere.
- `--shim` names the interposition library when it is not beside the binary (the tarball and zig-out layouts are found on their own). The search that finds it on its own **declines a candidate it cannot attribute** — a symlink, or a file owned by none of {you, root, the owner of the `sideeye` binary} — and says so rather than using it (#423, ADR 0044); a path you pass here is used as named and not checked. The check is a mitigation, not a boundary: it inspects a pathname, and the dynamic linker resolves that pathname again when the target starts. `--work` moves the scratch directory for traces and cases (default `/tmp/sideeye-work`). **It has to be yours** (#692, ADR 0099): the cases saved there are commands a replay runs, so a work directory Sideeye did not just create is refused before setup runs when its last component is a symlink (yours or not), when it is not a directory, when its name ends in `..`, when another user owns it — root included, unless you are root — or when its kind or owner cannot be read; the refusal names the directory and why, and Sideeye writes nothing under it (a `--json` report you point there is still written, as every refusal's is). A name that cannot be resolved at all is refused as before, naming the error. The way past is a name that does not exist yet, which Sideeye creates as yours, or a directory of your own. What used to run and now refuses: a link of your own at the name — pass the directory it points to — another user on the same host who made `/tmp/sideeye-work` first, `sudo sideeye` pointed at a directory you made, and a root container handed a bind mount your host user made. This too is a mitigation, not a boundary: it inspects the name once, and anyone who can write the directory's parent can swap it afterwards. **A symlink at the trace path is refused rather than followed — by every process the shim is loaded into when it writes the trace (#488), and by the engine when it reads that trace back (#489).** The engine removes the file before each run, but every process the shim reaches opens the name again afterwards and the later ones have nothing standing in front of them, so without the write-side refusal a link planted there would append the run's records to whatever it points at; without the read-side one, the account the verdict is drawn from would be whatever that link pointed at. A **FIFO** appearing at that path after the engine's own removal of it is refused on both sides as well: the read takes regular files only (#400), and the write does two things that answer different cases (#492): it opens **non-blocking**, so a FIFO with no reader fails outright instead of waiting for one — this is the half that stops the wait, in a constructor that runs before the target's `main`, inside a recording run with nothing to time it out — and it then asks what the descriptor turned out to be, closing it unless it is an ordinary file, which is the half that catches a FIFO somebody is already reading, along with a device or a socket. The one thing the write side leaves standing is a kind it could not read at all, a `statx` that fails: a host lacking it goes on refusing with `unresolvable_path`, which names a cause, rather than with a silence that names none. What is **not** refused: a **hard link** is the same file rather than a pointer to one, so no open flag sees it, on either side. Nor is the target on the other side of a boundary here — it holds the trace path in its own environment and can write the work directory, so a target that wants to hand Sideeye a trace it wrote itself is not something this or any flag stops.
- `--json <path>` writes the same report as JSON, for a machine to branch on. When the file is in place one line goes to stderr, in a single write: `sideeye: json sha256=<hex>;`, the digest of exactly the bytes written -- so a machine that receives the report through a directory the judged program can also write can tell the file it opens from one written after it. When the report could not be written the line reads `sideeye: json sha256=none;`. It is exactly one line per run that got as far as producing a document — a report, or `preflight`'s own (#717) — it is not part of the report schema, and a reader should count it wherever it appears rather than at a line start (a program sharing the descriptor can take the line start away, but not the token). It is the **last** thing sideeye writes, on every path -- the digest is recorded when the report lands and emitted at the exit, after the text report, so a reader that takes the first line of sideeye's output sees what it always saw — through a pipe or a file, where the verdict word is never coloured.
- The declared checker's output in each explored world is **also** captured to `<work>/checker-output.txt`, so the evidence bundle can quote the exhibit's last line. On your terminal each line is re-emitted with the world it came from — `world 3: ` for crash point 3, the number the report's `crash point 3 of n` carries, and `baseline: ` for the un-killed world — beside the falsification gate's `falsify: ` lines, the starting-state probe's `start: ` lines when it refuses (#756), and a recovery's `recovery world 3: ` and `recovery world 3 check: ` (its controls are `recovery falsify: `, `recovery baseline: ` and `recovery baseline check: `). The checker's stderr is captured into the same file in the order it was written and comes out on Sideeye's standard output with the same mark, not on Sideeye's standard error (#707). Empty lines are skipped, a line too long for the report's 32 KiB output buffer is dropped with a note on Sideeye's standard error, and a capture over 1 MiB is not re-emitted at all; the file keeps the checker's bytes unmarked, and holds whichever world ran last, which is the un-killed baseline. A capture that cannot be opened does not stop the run: the checker runs uncaptured, its standard output and standard error reach Sideeye's own directly and unmarked, the verdict rests on its exit status as before, and the bundle reports its diagnostic as unreadable.
- `--fresh-state` (replay only) empties and recreates the case's state directory before setup, for a caller that cannot hand over a pristine one — a second replay in the same directory would otherwise die in the leftovers of the first.
- Exit codes: **0 PASS, 1 FAIL, 2 UNKNOWN, 3 SETUP ERROR** — and UNKNOWN is never 0.
- When standard output is a terminal, `NO_COLOR` is unset or empty and `TERM` is not `dumb`, the text report's verdict word — PASS, FAIL, UNKNOWN, SETUP ERROR — is coloured; otherwise Sideeye adds no escape sequence of its own. Only standard output is asked, so `sideeye explore … > report.txt` typed at a terminal writes no colour to the file; a CI runner that gives its steps a terminal (Buildkite, `docker run -t`) colours the word, and `NO_COLOR=1` turns it off there. There is no flag to force colour (#712).
- `sideeye completions zsh|bash|fish` prints a completion script for that shell: it offers exactly the subcommands; after a subcommand, its positional argument where its usage line has one (a case file, a command name, a shell) and then exactly the flags its usage lines list — explore's and preflight's two lines together, so after `--config` the script still offers `--state`, which the run then refuses — with a value-taking flag's value completed as a file where the usage names a path, as its listed words where it lists them, and not at all otherwise. The script is built from the usage lines `sideeye help` prints, so it offers the flags this binary's help lists. Load it: bash (3.2 and later) `eval "$(sideeye completions bash)"` in `~/.bashrc`; zsh, after `compinit`, `eval "$(sideeye completions zsh)"` in `~/.zshrc`, or the output saved as `_sideeye` in a directory on `$fpath`; fish `sideeye completions fish > ~/.config/fish/completions/sideeye.fish` (#712).
- Command strings split on spaces, no quoting. An argument that carries a space uses the argv form instead: `operation = ["mytool", "commit", "-m", "a message with spaces"]` — one line, passed verbatim.
- **A string-form command that looks written for a shell runs as written, with a warning** (#706, ADR 0095). Its quotes reach the program as characters, and a whole word a shell would act on — `&&`, `||`, `|`, `|&`, `&`, `;`, `(`, `)`, a redirection such as `>`, `2>&1` or `1>/dev/null`, a word beginning `$` or `~/`, a lone `~`, a backquote, a `$` a shell would expand (one followed by a name, `{` or `(`) anywhere in a word, quoted in double quotes or not, a leading `NAME=value` — reaches it as an argument, unexpanded. Where a setup, operation, check or recovery command (a toml value or a flag) holds a quote or such a word, Sideeye says so in one sentence naming the command and, for quotes, the argv form that groups what they meant (for a flag, as the line a sideeye.toml would take; a `[recovery]` command has no argv form, and neither has a word the argv form cannot spell — an empty one, one with a `"` or `\` — so those are pointed at a script). Where a shell would have expanded a `$` or a backquote, no argv is offered: it would carry the unexpanded text. A glob is not looked at, and passes as written either way. A toml command value with an inner `"` followed at once by `#` — `check = "grep -c "#include" f"` — is read as ending at that quote, with the rest a comment; it is accepted as it always was, and the warning says what the command became. The sentence is in the report as `warning`, in the JSON as `define_warnings`, in `sideeye mcp`'s summary, and on Sideeye's standard error as `sideeye: warning: …`, written once at the end so the first line of merged output is still the verdict — which also reaches a run that ends in a SETUP ERROR, and `preflight`. A replay is not looked at: its case holds commands an exploration already read. Left alone: a symbol inside a word (`x=n*10`, `ggiX<esc>`, `~>1.6`, `%(title)s`), a version constraint (`>=1.6`), a glob, a brace, a backslash outside quotes (`a\ b`) — each means what it says to a program run without a shell. A toml value the parser refuses as not one double-quoted string — `state = './state'`, `expected_status = 0`, `operation = "tool "two words""` — is refused with the line it would have been read as, when that line parses back as one value the writer could have meant: a trailing comment is kept, a value that reads two ways (`"a" "b"`) and one holding bytes the report would have to rewrite get no line.
- A define spelled as argv lives in a toml; `preflight --config` reads it, as explore does.
- **A command, option or argument Sideeye does not accept is answered in one line that names what was typed and, when one is close, the nearest spelling that command accepts — never by the whole reference; `sideeye help <command>` (or `sideeye <command> --help`) prints that command's own synopsis and flags** (#705). A value is named as well as a flag (`--observe bogus` says `bogus`). The command's own help carries each flag's first sentence and every sentence of its entry that begins `Caution:`; `sideeye help` prints the whole reference, and `sideeye --version` is `sideeye version`. `sideeye <command> --help` is answered only as those three words: `explore --state X --help` and `explore --help --state X` are refused with that said, because the parser may already have acted on what came before it — `--json` removes the report at its path.

A FAIL saves its counterexample to `<work>/cases/NNNNNN.json`, writes an evidence bundle carrying the same id under `<work>/evidence/NNNNNN.json` — a directory of its own, so a reader of `cases/*.json` is never handed one, and prints the ready-to-paste `sideeye replay` line beside an `evidence` line carrying the command that renders the bundle, `sideeye evidence <bundle>`. `sideeye evidence <case.json>` renders that bundle as Markdown for a maintainer who has never used Sideeye — the paths whose before, completed and crashed states differ, whether each existed before the operation and whether its old bytes survive elsewhere inside the judged state, the two operations around the crash point, the checker's result and its last output line, the replay command and the run's own caveats. It runs nothing and produces no verdict: exit 0 when it renders, 3 when the bundle cannot be read. Every field is something the run measured or the word `unknown`, and nothing is ranked ([docs/evidence.md](evidence.md)). When some world failed your checker and it is not the overall earliest, that world is saved as its own case beside the first and the text report gains a `checker red` section naming it — two files, both replayable; one file when the two exhibits are the same world, and none of this when no world failed the checker. Replay re-runs the same pipeline restricted to that crash point; when the code changed underneath the case, it says `case no longer applies` instead of guessing. The path you hand it has to be an ordinary file: a pipe, a device or a process substitution is refused rather than read, because a case that cannot be read whole is not a case — and because reading one that never ends would leave the run with no exit code at all (#400). A relative `define.state` inside a case resolves **against the case file's own directory**, the way a relative path in a `sideeye.toml` resolves against the toml (ADR 0007) — so the same case names the same state directory from anywhere, and replay empties the directory the case meant rather than one named by whoever happened to invoke it. Cases this engine saves always store the resolved absolute path, so this rule is about the hand-written ones.

### The flags the define does not spell

Seven flags never appear in a `sideeye.toml`: they belong to the run rather than to the question.

- `--observe wrappers|syscalls|supervised` — where operations are counted. The default, `wrappers`, counts at the interposed libc entry points, with buffered stdio observed at flush granularity. `syscalls` (Linux) counts at the kernel boundary instead, through a seccomp filter and a `SIGSYS` handler inside the target's own process — the only way to see an operation libc issues from *inside* itself (an `fwrite` past the buffer), or one that never reaches libc at all: a raw `syscall(SYS_write, ...)`, or a runtime like Go's that issues every file call directly. Its trap set is every operation that can be a crash point. Check the second entry of the README's constraint list before reaching for it: under this mode an `exec`'d image the shim cannot be loaded into dies at its first state-changing call, which is the one limit that changes what the target does instead of making Sideeye refuse. `supervised` (Linux 5.19 or later, aarch64 and x86_64; #217, ADR 0089) counts the same operations from **outside** the target: the engine starts the operation through `sideeye __filter-exec`, which installs a seccomp user-notification filter and execs it, and no shim is loaded. **A statically linked target, which the other two modes refuse as `no_shim_marker`, is counted and reaches a verdict under this mode**, with the oracle watching the same run (one that starts a dynamic child, which those modes let past their gate because the child carries the shim, is sent here by three refusals in the shapes measured to be crossed, [report-schema](report-schema.md), #685; its other refusals keep their steps); where it cannot be judged it refuses with an existing reason. Each state-changing call waits for the engine, which counts it and lets it run, or at the crash point kills the run while the call is still waiting, so the call never runs. It needs a cgroup v2 the engine can create cgroups in (a setup error names it otherwise). Its walls: a run whose writes come from two or more threads refuses `multiple_threads_detected`, because the thread-order records are the shim's — and recording thread creations and exits from outside instead is not built: of 50 recording runs this mode refused for jj, OpenTofu, codex and doctl, 48 hold a hand-over between writing threads that neither a thread's creation nor its exit orders, and doctl's other two were ordered by a creation the Go scheduler happened to make (#687, `spike/dogfood/2026-10-10-thread-order/`; tombi, refused in 1 of 36 supervised explores and 3 of 20 replays while its preflight was accepted 26 times of 26, was not read); a target that installs its own seccomp filter can return an error or trap for a call before this one sees it; `no_new_privs` is set, so a setuid child does not gain its privilege; i386-compat and x32 calls are not seen. Reading a call's paths needs the engine to read the target's memory, which Yama's `ptrace_scope` governs: at 2 or 3 every in-scope operation is unplaceable and the run refuses rather than guesses. The filter outlives the engine only as long as the engine does: were the engine to die mid-run, the target's next watched call would fail with `ENOSYS` — a changed target, which the run that follows cannot report because nobody is left to report it. On a run that reached the oracle comparison — whether it agreed or refused — and under `--allow-unverified`, the report's `oracle` line says who counted: the supervising engine, from outside the target, with no shim loaded. A run refused before the comparison (a thread refusal, say) says `not compared`, as in every mode. **A case saved under `--observe syscalls` or `--observe supervised` records the mode, and is replayed under it with no `--observe` given** — by `sideeye replay <case>` and by `sideeye_replay_case` over MCP alike (#691, ADR 0100). The report's `replay` line still names the mode, which a replay accepts when it matches; an `--observe` naming another mode is refused by name, because the case's crash point is a number in its own mode's count. Such a case is `case_version` 6, which a binary before this change refuses as unparseable rather than replays; a case counted under the default keeps the version its define asks for. A case saved before this change records nothing, and is replayed under the flag, or the default, as it always was.
- `--oracle <strace>` — the Linux oracle: the recording run is wrapped in strace and the shim's account is compared against strace's. **Refused on macOS** as `platform_unsupported`, whatever the path names (macOS has no strace, and the engine reads strace's account and nothing else); the refusal names `--oracle-fs-usage` and `--allow-unverified` under explore and replay, and says to drop the flag under preflight, which takes neither (#702).
- `--oracle-fs-usage` — the macOS oracle, in place of `--oracle`. It compares the recording run against `fs_usage`, which needs root, so `sudo` must already hold credentials (`sudo -v` first, in the same terminal — the cache is per-terminal); the run refuses rather than prompting. It is narrower than strace. `fs_usage` prints only a rename's old path and cuts long pathnames from the left (both measured), so a rename it cannot match and a state directory deep enough to be cut are refusals rather than agreements. It cannot account for other processes, so a child the shim saw, or the subject replacing its own image, is UNKNOWN under it. A single-process run with neither, whose state-directory writes come from one thread the shim recorded — the main thread or a worker — is explored and judged under it as under `--oracle` (ADR 0060).
- `--allow-unverified` — accept a PASS with no completeness check. On macOS this is the answer when no privilege is available: SIP leaves DTrace's syscall provider with no probes even as root, and the one candidate that measured oracle-shaped, `fs_usage`, requires it. The report says which claim was made, and this one is weaker.
- `--world-timeout <s>` — a wall-clock budget per explored world (1 to 86400, off by default). A world's operation still running when the budget expires is sent `SIGKILL` and refused UNKNOWN `child_timed_out`, with the budget in the message. Worlds only: a recording run, a setup command or a checker that hangs still hangs, so this is not a promise of a hang-free run. Setting it also resets `SIGCHLD` to its default disposition for the whole run, and it is not settable over MCP today.
- `--stop-when-orphaned` — stop at the next world boundary if the process that launched the run exits (UNKNOWN, `parent_exited`). The MCP server passes it on every explore and replay: agent hosts restart MCP servers routinely, and an orphaned exploration otherwise keeps killing processes and rewriting its state directory with nobody left to report to. A run that hangs before a boundary is out of reach.
- `--state-under <dir>` (explore, replay, and `preflight --twice`) — the directory the state must resolve strictly inside; anything else is refused before setup runs. A case file names its own state directory, and a config its own, and all three commands empty and rebuild it — explore and replay every world, `preflight --twice` before its second run — so this is how a caller that vetted only the file's path bounds where it may point the deletion. Preflight without `--twice` rebuilds nothing and refuses the flag. The MCP server passes its `SIDEEYE_MCP_STATE_ROOT` (default: the server root) on every exploration (#765), every replay and every `twice` preflight (#717).

## Example

Real output — the same planted delete-before-rename bug the demo uses (`spike/toys/toy.c`), explored with a checker and the strace oracle; the paths are the container's, and the engine hands the target its state directory via `SIDEEYE_STATE_DIR` and, for the toy, `TOY_STATE`:

```
$ TOY=/tmp/se/toy-bug /work/zig-out/bin/sideeye explore --state /tmp/se/state \
    --setup "/tmp/se/toy-bug init" --operation "/tmp/se/toy-bug rotate" \
    --check /work/spike/check.sh --shim /work/zig-out/lib/libsideeye_shim.so \
    --work /tmp/se/work --oracle /usr/bin/strace

falsify: doctor says 'healthy' but the key is unloadable
world 5: doctor says 'healthy' but the key is unloadable
FAIL  1 of 6 explored worlds violated an invariant

invariant   built-in atomicity, and the checker
earliest    crash point 5 of 5
            after  unlink(/tmp/se/state/key.json)
            before rename(/tmp/se/state/key.json.tmp)
path        key.json
observed    present before and after the operation, but gone from the crashed state
cwd         /work  (none declared: Sideeye's own)

explored    6 worlds (crash points 5 + 1 baseline)
expected    exit 0
atomicity   1 path(s) judged pre-or-post
oracle      agreed on 5 operations (88 syscall lines examined, 12 in scope of the judged state), witness strace
metadata    none observed. Restore does not reproduce ownership/permission/timestamp state: crash worlds run at the engine's default modes, with timestamps assigned during restore
checker     falsified before the run (corrupted state -> check failed); ran in 6 world(s)
l1          no marker configured
case        /tmp/se/work/cases/000001.json
replay      sideeye replay /tmp/se/work/cases/000001.json --shim /work/zig-out/lib/libsideeye_shim.so
evidence    sideeye evidence /tmp/se/work/evidence/000001.json
processes   single process
not tested  power loss, torn writes, concurrent processes

reproduce   (cd /work && unset SIDEEYE_KILL_GROUP && : > /tmp/se/work/trace-repro.bin && SIDEEYE_STATE_DIR=/tmp/se/state SIDEEYE_STATE_DIR_ALT= SIDEEYE_TRACE_PATH=/tmp/se/work/trace-repro.bin LD_PRELOAD=/work/zig-out/lib/libsideeye_shim.so SIDEEYE_KILL_AT=5 SIDEEYE_SEQ_BASE= SIDEEYE_OBSERVE=wrappers SIDEEYE_RUN_CGROUP= SIDEEYE_KILL_CGROUP= SIDEEYE_KILL_ASIDE= /tmp/se/toy-bug rotate </dev/null)
```

Read the account block, not just the verdict: `explored` says how much was looked at, `oracle` says a second witness (strace) checked the shim's account against the kernel's, `checker` says the invariant was proven able to fail before the run began, `cwd` says where the define's commands ran — Sideeye's own directory here, because this define declared none — and `not tested` names what this verdict is silent about. A PASS and an UNKNOWN print the lines they share with this block under the same keys, in the same columns and the same order — `cwd`, `apparatus`, `warning` and `recovery` first, then a blank line, then the rest — and each verdict prints a fixed set: a PASS has no `replay` or `evidence`, which belong to a counterexample, and an UNKNOWN leaves out `explored`, `oracle`, `metadata` and `checker`, because a refusal can be raised before the exploration and would print figures for crash points it never reached (the JSON report carries all of them on every verdict). On an explore's FAIL that saved its case, `replay`, `evidence` and `reproduce` are commands that run as printed (#709, #711). `replay` and `evidence` run with `sideeye` on `PATH` — `replay` from the directory the `cwd` line names when the define declared none, since an undeclared define's commands run where Sideeye is started, and with the `--observe` mode the run used, which a replay also takes from the case itself when the mode is not the default. `reproduce` runs in a POSIX shell once the define's setup has left the state it starts from — as often as it is pasted: in a subshell, it changes to the directory the commands ran in, empties its trace file (the shim numbers on from the highest number a trace already holds, so a second paste into a full one would never reach the crash point), sets the variables Sideeye hands a world — except that a pasted line runs in neither a world's process group nor its cgroup, so it unsets `SIDEEYE_KILL_GROUP`, whose mere presence would take the reader's own shell down with the target, and pins the cgroup ones empty; and it does not carry `TOY_STATE`, the demo toy's own name for the state directory, which the toy reads `SIDEEYE_STATE_DIR` for when it is unset — and runs the operation's own argv with standard input from `/dev/null`, as every command Sideeye runs has it. Its standard output is the terminal, where a world's was a file. It dies in front of the same crash point, in the process that reaches it: where the run admitted writing children, the rest of the tree keeps running, so the state can go further than the report's. Every value is quoted where a shell would read it otherwise, and a bare first word is quoted too, so an alias of that name in an interactive shell is not what runs. The line keeps the placeholder `<operation>`, with no `cd`, when the operation or its directory holds a byte the report defangs (rather than print the byte, or a defanged command that names something else), when Sideeye could not name the directory, or when the command would not fit the text report's output buffer. A replay's own FAIL prints the sentence it always did on `replay` and `-` on `evidence`; a FAIL whose case could not be written, `-` on both; under `--observe supervised`, `reproduce` names the replay line, the one command that reproduces a crash point counted from outside the target.

The `check` script is where your invariants live. This one cross-examines the tool's own diagnostic — a tool is allowed to be broken as long as it says so; the violation is the claim and the observable truth disagreeing:

```sh
#!/bin/sh
claim=$("$TOY" doctor 2>/dev/null) || claim="unhealthy"
"$TOY" load-key >/dev/null 2>&1 && reality="loadable" || reality="unloadable"

case "$claim:$reality" in
    healthy:loadable | unhealthy:unloadable) exit 0 ;;
    *) echo "doctor says '$claim' but the key is $reality" >&2; exit 1 ;;
esac
```

The full version is [`spike/check.sh`](../spike/check.sh). Sideeye refuses to trust a checker it has not seen fail: before exploring, it corrupts the state and requires the check to reject it. A checker that cannot fail makes the run UNKNOWN, not PASS. More worked checkers: [docs/checker-cookbook.md](checker-cookbook.md).

## What it is for after the first find

The finding is not the durable artifact — the declaration is. A `sideeye.toml` and its checker are the question, not the answer, so re-asking it after the tool changes is `explore --config` again, and the report says what it looked at that time rather than assuming the last run still holds. A saved case is deliberately narrower: it names one crash point in one recording, and when the recording moves underneath it the answer is `case no longer applies` rather than a silent pass — which is what makes a case worth keeping in CI. This repository keeps its own oldest finding that way, re-recorded under the current trace contract on every push to main and every pull request (the `timew-regression` job in `.github/workflows/ci.yml`). And because a target Sideeye cannot fully observe is UNKNOWN and never exit 0, a machine caller can tell *checked and clean* from *not checked*, which is the distinction an unattended run has to get right. What none of that does is constrain what your declared operation may do — that boundary is the config you vet, as [the MCP page](mcp.md) says.
