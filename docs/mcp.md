# The MCP server

The README gets a person to a first verdict at the command line. This page is the same engine driven by an agent over MCP: what the server reads, what it confines and what it does not, and a first call that CI runs against the built server.

## Driving it from an agent (MCP)

`sideeye mcp` is a stateless MCP server (stdio) with four tools: `sideeye_preflight {config_path, observe?, twice?}`, `sideeye_explore_config {config_path, observe?}`, `sideeye_replay_case {case_path}` and `sideeye_evidence {case_path}`, the first answering without exploring and the last running nothing (below). The tools take *paths* inside `SIDEEYE_MCP_ROOT`, never raw commands — the config file is the trust boundary you vet, **and a saved case is the same boundary**: its setup/operation/check are executed on replay, exactly as a config's are on explore. The root confines which config or case may be named, not what its commands do: run the server inside a container — [one to copy](#running-it-in-a-container) is below — network-off where the target allows it. **The server does not check that you did**, and #328 measured why a check would not help: the observations that *do* move with confinement can be raised by the process being confined — a `Seccomp` filter costs two `prctl` calls and no capability at all, Docker's masked `/proc` mounts cost `CAP_SYS_ADMIN`, which the unconfined process is the one to have — and none of them says anything about the mount the root came in on. A container reading maximally confined by every one of them (`/.dockerenv` present, `Seccomp: 2`, ten masked `/proc` entries, no extra capabilities, its own PID namespace) destroyed a file on the host through a bind-mounted root — the shape this page recommends. **What the containment cannot do for you is make the root safe to lose**: pick that directory as if a replayed case will empty it, because one can. A single-component mount is fine (`/work`, `/repo` — a directory the container exists to hold); what the server refuses at startup is `/`, a system tree or scratch parent (`/usr`, `/var/lib`, `/tmp`), **and any directory that contains one** — so `/var` and, on macOS, `/private` are refused for holding `/var/lib` and `/private/tmp`. The denylist stops the mistake that has a name, not every bad choice: **with `SIDEEYE_MCP_STATE_ROOT` unset the root is also the declared destruction range**, so name a directory whose contents are yours to lose — `/opt` passes the vet and is where installed software lives. One thing more IS confined (#266): every state directory the server has the engine empty and rebuild — the one a replayed case names, and the one a config names when `sideeye_explore_config` explores it (#765, ADR 0106) or `sideeye_preflight` runs it with `twice` (#717) — must resolve strictly inside `SIDEEYE_MCP_STATE_ROOT` (default: the root), or the call is refused before setup runs. Cases made at the CLI conventionally keep state under `/tmp`, and so may a config; set `SIDEEYE_MCP_STATE_ROOT=/tmp` to replay or explore them through the server. The range is one directory: with it set to `/tmp`, a config whose state is under the root and not under `/tmp` is outside it, so choose a directory that holds every state you mean the server to rebuild. Widen that knob, never the root (ADR 0022).

**A config's `[recovery]` is part of that boundary too** (#606, ADR 0072): `sideeye_explore_config` runs its `command` and `check` against each saved FAIL, after the verdict, exactly as it runs the define's checker — vet them the same way. Two differences from the command line: the server passes no `--world-timeout`, so a recovery that never ends holds the call the way a hanging checker does; and `sideeye_replay_case` has no recovery parameter and a saved case does not carry the recovery, so a replay through the server runs none — replay one with `--recovery` / `--recovery-check` at the command line instead. Surface 5 would allow the parameter as a new optional one; this change does not add it.

**`sideeye_preflight` answers without exploring** (#717). It runs `sideeye preflight --config` on a config inside the root — one observed run, or with `twice: true` a second one from the restored state compared with the first — so an agent revising a define can learn whether the recording is accepted, which paths the built-in invariant would judge, and under `twice` which paths two runs leave differently, without running every world. The config's setup and operation are executed, as for `sideeye_explore_config`. **`twice` empties and rebuilds the config's state directory before the second run, so the server passes it the same range a replay gets: the state has to resolve strictly inside `SIDEEYE_MCP_STATE_ROOT` (default: the root), or the call is refused before setup runs.** A config an agent just wrote is not one an operator vetted; since #765 `sideeye_explore_config` is confined the same way, so the config a `twice` call accepted is one the exploration accepts on the range too. Without `twice` the range is not checked, and the call's `next:` line says the exploration will check it. The answer is preflight's own JSON ([docs/report-schema.md](report-schema.md#preflights-document-preflight---json)): a refusal or a stop is a report, summarised and `isError: true` like any; an accepted recording, or two runs that differ, is `sideeye/preflight` with `isError: false` — both are answers to the question asked, as a FAIL is. Its text block puts the outcome and the counts above one counted region in which every string the target or the define could shape is quoted — the account sentences, the cwd, `scratch`, the judged paths, each differing path and its shape — apart from the define's apparatus and warnings, which go on lines of their own as the report's summary puts them, and names what to call next on a `next:` line. No byte of a stretch two runs disagree on is in the answer; the server also removes the child's text output, which quotes them, as soon as the child exits. Under `SIDEEYE_MCP_ORACLE` the oracle's capture in the work directory still holds the start of each write, as it does for an exploration.

**`sideeye_evidence` runs nothing** (#717). It reads the evidence bundle a FAIL saved beside its case ([docs/evidence.md](evidence.md)) — given the case's path or the bundle's own, both inside the root; the bundle's path is resolved and confined again, so an `evidence/` directory linked out of the root is refused as any other path outside it is. No target, setup or check is started and no state is touched, so it carries none of a replay's risk. The bundle sits in the work directory, which the target can write, so everything in it is treated as the target's: the text block puts closed words and numbers above one counted region that holds every string, each quoted, and `structuredContent` carries the bundle re-encoded with its `case` and `replay` replaced by the server's own — `replay` names `sideeye_replay_case` with the resolved case path, never a command line, since a command line taken from the bundle and run on the host would run outside whatever holds this server. Both are empty when there is no case to offer: none beside the bundle inside the root, or one whose resolved path holds bytes outside printable ASCII (the work directory is the target's to write, and the replay line sits outside the counted region). The bundle and its case have to be inside the root to be read at all, and so does a case to be replayed: a server whose `SIDEEYE_MCP_WORK` is outside the root — the default `/tmp/sideeye-mcp` is, in [the container below](#running-it-in-a-container) — saves cases it cannot read back through either tool. For the Markdown to paste into an upstream report, run `sideeye evidence <case>` at the command line. `isError` is false when the bundle is read and true when it cannot be: none beside the case inside the root, unreadable, over 4 MiB (the command line reads up to 16 MiB), not a bundle, or written by a newer sideeye.

### The first call

The server speaks MCP schema **2026-07-28**. Two consequences a client written against an older mental model will meet immediately: there is no `initialize` — the server exposes `server/discover`, and `tools/list` works without either — and **`_meta` is per-request and mandatory**, with the protocol version and client capabilities under their namespaced keys exactly as spelled below.

Everything the server reads from its environment:

| Variable | Required | Meaning |
|---|---|---|
| `SIDEEYE_MCP_ROOT` | **yes** | The directory tool paths are confined to, vetted at startup (above). |
| `SIDEEYE_MCP_SHIM` | no | An override. Unset, the server looks where `docs/cli.md`'s install note says it looks: beside the binary, then `../lib` — the same order the CLI uses, so a tarball and a Homebrew install both resolve with nothing set. Until #389 this command demanded the variable instead, which made it the one place the product did not do what that sentence promises. **The search declines what it cannot attribute** (#423, ADR 0044): a candidate that is a symlink, or that belongs to none of {you, root, the owner of the `sideeye` binary}, is refused by name rather than used, and the refusal says which of the two places it was and how to get past it. This is a mitigation and not a boundary — what is checked is a pathname, and the dynamic linker resolves that pathname again when the child starts, so anyone who can write the install directory between the two has not been stopped. Where that directory is not yours alone, set this variable, or fix the permissions. |
| `SIDEEYE_MCP_STATE_ROOT` | no | Where a replayed case's state directory, and the state of a config `sideeye_explore_config` explores or `sideeye_preflight` runs with `twice`, may live. Default: the root (ADR 0022, ADR 0106). |
| `SIDEEYE_MCP_WORK` | no | Scratch for traces and cases. Default `/tmp/sideeye-mcp`. **It has to be yours** (#692, ADR 0099): unless the server has just created it, the call is refused before any child runs when its last component is a symlink, when it is not a directory, when its name ends in `..`, when another user owns it, or when its kind or owner cannot be read — the server writes each child's capture there and reads the verdict back from it, so whoever controls the directory controls the answer. Name one that does not exist yet and the server creates it. A mitigation, not a boundary, for the reason the shim search is one: a name is checked once. |
| `SIDEEYE_MCP_ORACLE` | no | The second witness, strace's path — Linux only: on macOS every call it reaches is refused as `platform_unsupported`, so leave it unset there. Without one a would-be PASS refuses as `completeness_not_verified`; a FAIL stands on its own evidence either way. |
| `SIDEEYE_MCP_CHILD_ENV` | no | Comma-separated names of variables to pass through to the target. Nothing else reaches it (ADR 0011). |

**`sideeye_explore_config` takes an optional `observe` — the same closed choice as the command line, `wrappers` (the default), `syscalls` or `supervised` — so a refusal whose `next_step` names `--observe syscalls` can be followed through this server** (#617, ADR 0074). That refusal is `oracle_missed_operation` under the default mode (#599, ADR 0069). It is not the only step that names a mode: `observe_supervised` (ADR 0090) and `observe_supervised_static_parent` (#685, ADR 0108) name `--observe supervised`, which this parameter takes too. Seven things about the parameter, each of which is a decision rather than an omission:

- **Omit it and nothing changes.** The server passes no `--observe` at all, which is what the default means, so a call written before this parameter reaches the same run it always did.
- **A value it does not take is refused before anything is spawned** — `-32602`, the same shape as a missing `config_path` — rather than by a child that has already started against your target. The two names are the CLI's, case-sensitively, and a JSON `null` is a value rather than an omission.
- **`syscalls` can change what the target does, and it is the only option here that does.** It installs a seccomp filter, and a process whose `SIGSYS` is blocked or reset dies at its first state-changing call — an `exec`'d image the shim cannot be loaded into, a `posix_spawn` child (README, "What the target has to be"). Everything else on this page changes what Sideeye reports; this changes the run. The engine's own `next_step` says so to a caller who arrived at the mode through a refusal; a caller who picks it from this schema is reading it here.
- **It is not a promise of a verdict.** That mode has refusals of its own, and what it does not see is listed under "What `--observe syscalls` does not see" in [docs/report-schema.md](report-schema.md). It is Linux-only — on macOS the run ends `SETUP_ERROR` with `platform_unsupported`, naming the reason rather than falling back to the default.
- **`sideeye.toml` still has no key for it**, deliberately: the config format is a frozen surface (`docs/contract-freeze.md`, surface 1), and a key there would also change what the file means at the command line.
- **`sideeye_replay_case` does not take it, and does not need it.** A saved case is a recording made under one mode, and a case saved under `syscalls` or `supervised` records that mode and is replayed under it (#691, ADR 0100) — so a case this tool's explore saved under either replays through `sideeye_replay_case` with nothing more sent. A case saved before that change records nothing and replays under the default here; replay it at the command line with its `--observe` instead. Its schema declares `additionalProperties: false`, so sending `observe` there is not something to rely on: this server ignores unknown keys, a validating client will refuse the call before it arrives, and neither behaviour is promised.
- **Which server you are talking to is legible in `tools/list`** — the schema carries the parameter or it does not. That is the way to tell, because a server without it ignores the key silently and no report says which mode ran.

One value is yours to supply, and it is written as `/path/to/…`. Nothing else has to be set:

```sh
export SIDEEYE_MCP_ROOT=/path/to/your/workspace
```

With a `sideeye.toml` in that workspace — the README's Usage section shows the shape; fill it in for your own tool — this reaches a verdict, or refuses with a named reason:

```jsonrpc
{"jsonrpc":"2.0","id":1,"method":"tools/list","params":{"_meta":{"io.modelcontextprotocol/protocolVersion":"2026-07-28","io.modelcontextprotocol/clientCapabilities":{}}}}
{"jsonrpc":"2.0","id":2,"method":"tools/call","params":{"_meta":{"io.modelcontextprotocol/protocolVersion":"2026-07-28","io.modelcontextprotocol/clientCapabilities":{}},"name":"sideeye_explore_config","arguments":{"config_path":"/path/to/your/workspace/sideeye.toml"}}}
```

`isError` follows the verdict structure, not the outcome: a FAIL is a real answer and comes back `false` (ADR 0010). **Both blocks are run on every pull request and every push to main, extracted from this page, against the built server, with nothing else in the environment** — on Linux as `spike/mcp-acceptance.sh` check 15 and on macOS as a step of its own, both calling `spike/check-readme-mcp-call.sh`. They are a record of what the server does today, not an addition to the frozen surface — what v1.0 froze is the two tool names, their input schemas and that `isError` rule (`docs/contract-freeze.md`, surface 5).

Measured here, not aspirations: a context-free agent, handed a counterexample and bug-blind replay plumbing, produced the fix — twice: once through the CLI, once through this MCP server (`spike/loop-closure-timew/`) — an LLM scout authored the defines for five real targets under a fixed protocol (`spike/assisted/`; the method: [docs/scouting.md](scouting.md)), and a context-free agent set Sideeye up **from the README alone** — tarball to a real verdict on an external tool in under five minutes, protocol declared before the clock, measured twice (`spike/onboarding-clock/`: run 1 at 4 m 22 s, 2026-08-17; run 2 at 2 m 55.7 s, 2026-08-28, against the README as it stood at the freeze — the criterion's evidence).

## Running it in a container

The root confines which config or case may be named; what their commands do is bounded by whatever holds the server, and the section above says a container. [`docs/mcp-container/Dockerfile`](mcp-container/Dockerfile) is one to copy, not an image to pull (#721, ADR 0114): the tool your `sideeye.toml` runs has to be inside the same image as the server, so the image is yours to build. It takes a release's own tarball, checked by `ADD --checksum` against the digest GitHub publishes for it, adds `strace` and points `SIDEEYE_MCP_ORACLE` at it, and leaves its last lines for your tool. Build the tool on the same base: a program linked against a newer glibc than the base carries can refuse to start. It needs BuildKit, Docker's default builder; the file's first line has BuildKit fetch a Dockerfile frontend that knows `ADD --checksum`.

The server inside is the release the Dockerfile names, and this page describes `main`. What came after that release — tools, refusals and checks alike, the CHANGELOG's entries after it — arrives when `SIDEEYE_VERSION` and its two digests move.

A deployment that follows from the above, rather than only from the word "container":

```sh
# In a directory holding image/ (your copy of the Dockerfile, your tool added at its end,
# and whatever those lines copy in) and sideeye-work (your sideeye.toml and the state it
# names, and nothing else). --user runs the server as you, so it can write the mount you
# made and everything it leaves there is yours; drop it under rootless Docker or Podman,
# where the container's root already is you. --network=none where the target allows it;
# --read-only and --cap-drop bound what a target can do to the image; --tmpfs /tmp is
# required, not decoration — the work directory defaults to /tmp/sideeye-mcp, which
# --read-only would leave unwritable. The server runs nothing from there; :exec is for a
# define that runs what it puts under /tmp.
docker build -t sideeye-mcp image &&
docker run --rm -i \
  --user "$(id -u):$(id -g)" \
  --network=none \
  --read-only --tmpfs /tmp:exec \
  --cap-drop=ALL --security-opt no-new-privileges \
  -v "$PWD/sideeye-work:/work" \
  -e SIDEEYE_MCP_ROOT=/work \
  sideeye-mcp sideeye mcp
```

The mount is the part that matters and the part a container cannot make safe: everything reachable through it is reachable by a replayed case's commands. Give the server a directory created for it — not your repository, not your home, not a checkout you would mind losing — and treat its contents as already gone. `--read-only` and `--cap-drop=ALL` bound what a target can do to the *image*; nothing bounds what it does inside the root you handed it, which is why `SIDEEYE_MCP_STATE_ROOT` exists (ADR 0022) and why it is the knob to narrow first.

Run on every change to this page, the Dockerfile or the quickstart's pinned version, on x86_64 and aarch64 Linux runners (`.github/workflows/mcp-container.yml`, running `spike/check-mcp-container.py`): the block above as written, with a toy added at the end of the Dockerfile and two defines in the README's shape (`state = "./state"`, so the state is inside the mount), answers the first call of the section above with a FAIL on a target with a planted bug and with a PASS whose `oracle_verified` is true on a correct one; under the same flags the container runs as a user other than root, holds no capability in its effective or bounding set, has `NoNewPrivs` set and no route, and its root file system refuses a write; and the Dockerfile's version and digests are the release's. The server runs as the runner's user inside, as the block starts it. That workflow does not run Docker Desktop, rootless Docker, Podman, or a replay.

## The agent skills

Three skills ship from this repository, for an agent that drives Sideeye through the CLI or through this server: `sideeye-scout` sets Sideeye up on a tool and takes it to a verdict, `sideeye-triage` takes a FAIL on code you can change to a fix, and `sideeye-report` drafts a report for another project's maintainers from a FAIL on their tool — after reading that project's contribution rules and its policy on AI-written text, and stopping where a drafted report would break them. Each is a `SKILL.md` under [`skills/`](../skills/). They install with the installer's version pinned, because `npx` runs it from npm with your permissions and an unpinned name runs whatever was published last:

```
$ npx skills@1.7.1 add yottayoshida/sideeye
```
