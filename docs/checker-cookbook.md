# The checker cookbook

A checker is the declared invariant's sharp end: a command Sideeye runs over each crashed state, exit 0 meaning the invariant holds. It is the layer that found the timewarrior bug, and the layer easiest to get quietly wrong. Everything below is a real committed checker, or a failure pattern with the run that taught it — nothing was invented for this page.

Before any exploration, Sideeye **falsifies** the checker: it corrupts a copy of the state on purpose and requires the checker to go red. A checker that cannot fail anything is refused (`checker_not_falsified`), never trusted. Then it shows the checker the state the define starts from — restored the way every world starts from it, so what a restore does not carry ([docs/cli.md](cli.md)) is not there, whatever your setup left — and requires it to pass: a checker that rejects that state is refused too (`checker_rejects_initial_state`, #756), because the world killed before the first operation holds exactly that state, and nothing the target did is in it. A checker has to hold before the operation as well as after it — accept the old value and the new one, not only the one the operation writes. The recipes below are about the subtler failures that gate cannot catch.

A refusal that is not about the checker but about two clean runs leaving different bytes (`baseline_violates_invariant` on the byte layer) is read with [docs/apparatus.md](apparatus.md#reading-a-byte-difference), which maps what the difference looks like to `scratch` and `apparatus`.

A checker finds the state directory in `SIDEEYE_STATE_DIR`, the absolute path of the `state` you declared, resolved through any symlink — the setup, the operation and a recovery receive it too. Recipe 1's header also names `TOY_STATE`: the name the demo toy reads, which Sideeye sets to the same path for every command, so the checkers written against it keep working. A new checker reads `SIDEEYE_STATE_DIR`.

## Recipe 1 — cross-examine the tool's own diagnostic

`spike/check.sh`, the acceptance toy's checker (the README quotes part of it): run the tool's `doctor`, run the operation that depends on the same state, and require the two to **agree** — healthy things must work, unhealthy things must say so. A target is allowed to be broken as long as it says so; the violation is the *mismatch*, a diagnostic answering "healthy" over a store the tool itself cannot read.

`spike/check.sh`:
```sh
#!/bin/sh
# The L2 checker: cross-examine the diagnostic command against reality.
#
# The invariant is not "the key is readable" — a target is allowed to be broken as
# long as it says so. The invariant is that `doctor`'s claim and the observable truth
# agree. Both directions are violations: claiming health while the key cannot be read,
# and claiming trouble while it can.
#
# Runs after the crash, in a fresh process, exactly as DESIGN §12 requires. Exit 0
# means the invariant holds.
#
# Environment:
#   TOY    path to the toy binary
#   TOY_STATE  state directory (passed through to the toy)

set -u

: "${TOY:?check.sh needs TOY to point at the binary under test}"

if claim=$("$TOY" doctor 2>/dev/null); then
    :
else
    claim="unhealthy"
fi

if "$TOY" load-key >/dev/null 2>&1; then
    reality="loadable"
else
    reality="unloadable"
fi

case "$claim:$reality" in
    healthy:loadable)     exit 0 ;;
    unhealthy:unloadable) exit 0 ;;
    *)
        echo "doctor says '$claim' but the key is $reality" >&2
        exit 1
        ;;
esac
```

## Recipe 2 — the non-destruction form

`spike/loop-closure-timew/define/check.sh`, the checker behind the timewarrior finding — its one canonical text, beside `setup.sh` and `operation`; the scripts that stage or replay the define (`stage.sh`, `dogfood-timew-replay.sh`) copy the checker and setup and read the operation from there rather than carrying their own, and the frozen v0.4 recipe `spike/dogfood-timew.sh` keeps a copy the unknown-rate corpus pins, a record rather than a consumer (#65): after `timew undo`, the export must have removed *either nothing or exactly the newest interval*. The first draft demanded that undo always remove something — which condemns a correct recovery along with the bug, because a crash may have beaten the intent's commit; `spike/dogfood-timew.sh` carries that rationale beside the checker text. The admission is written down too: this form deliberately allows an undo that always no-ops, so the loop-closure apparatus scores a fix that *lobotomizes* the feature as a failure on a separate gate — declared before the run, not discovered after (`BUILDLOG.md`). One limit the code below makes visible and the sentence above does not: the comparison is over the *set* of interval keys, so it is blind to multiplicity — an undo that left a duplicate of an interval already present would add no new key and pass. The claim the checker actually carries is about which keys appear and disappear, not how many times each does.

```sh
#!/bin/sh
# The declared invariant (L2 checker), non-destruction form: undo must remove either
# nothing or exactly the interval timew's own export names as most recent — never an
# older committed interval, and it must not invent intervals. Removing nothing is
# allowed because a crash may have beaten the intent's commit.
#
# This file is the one canonical text of the checker (#65). The scripts that stage or
# replay the define copy it from here; none carries its own. The frozen v0.4 recipe,
# whose bytes the unknown-rate corpus pins, is a record rather than a consumer.
set -eu
before=$(timew export) || exit 1
timew undo >/dev/null || exit 1
after=$(timew export) || exit 1
BEFORE="$before" AFTER="$after" python3 - <<'PY'
import json, os, sys

def key(iv):
    return (iv["start"], iv.get("end", ""), ",".join(iv.get("tags", [])))

before = json.loads(os.environ["BEFORE"])
after = json.loads(os.environ["AFTER"])
if not before:
    print("export was empty before undo: the seeded interval is gone", file=sys.stderr)
    sys.exit(1)
newest = min(before, key=lambda iv: iv["id"])  # id 1 is timew's own "most recent"
b = sorted(key(iv) for iv in before)
a = sorted(key(iv) for iv in after)
added = [k for k in a if k not in b]
removed = [k for k in b if k not in a]
if added:
    print("undo added intervals:", added, file=sys.stderr)
    sys.exit(1)
if removed not in ([], [key(newest)]):
    print("undo removed the wrong change: timew's own export named", key(newest),
          "as most recent, but undo removed", removed, file=sys.stderr)
    sys.exit(1)
PY
```

## Recipe 4 — leg order is part of the contract

`spike/assisted/buku/ops/check.sh` runs its query legs FIRST, deliberately: sqlite's documented contract is recovery-on-next-open, so the bystander query IS the documented next open, and an integrity check placed before it would measure a state the contract never promises. The same file records a dropped leg — asserting the journal file's absence was an undocumented hygiene claim, not the declared property. Order and scope are both part of what you declare.

To adapt this: Swap `XDG_DATA_HOME`, the database path, the bystander query and its expected row for your target's, and take the state from `$SIDEEYE_STATE_DIR` (`export XDG_DATA_HOME="$SIDEEYE_STATE_DIR"` here) rather than a fixed path; the leg ORDER is the part to copy unchanged.

`spike/assisted/buku/ops/check.sh`:
```sh
#!/bin/sh
# Assisted run (#118), buku P1 checker. Property (proposals.md P1): bookmarks
# you already had survive a crash during a new add, and the db stays a
# well-formed sqlite database.
#
# Leg order is deliberately query-FIRST here, unlike the blind campaigns:
# sqlite's documented contract is recovery-on-next-open (a hot journal is
# rolled back by the next opener). The bystander query below IS that
# documented next open, performed by buku itself; only after it does the
# file-level integrity check make a fair claim. A read-only integrity probe
# before recovery would fail worlds the contract explicitly permits.
set -u
export XDG_DATA_HOME=/tmp/assisted/buku/state
DB=$XDG_DATA_HOME/buku/bookmarks.db
TAB=$(printf '\t')

fail() { echo "checker(buku-add): $*"; exit 1; }

[ -f "$DB" ] || fail "db is missing (the store existed before the operation)"

out=$(timeout 10 /usr/bin/buku --nostdin --np -s GraceMark -f 4 < /dev/null 2>&1)
rc=$?
[ "$rc" -eq 0 ] || fail "bystander query exited $rc: $out"
matches=$(printf '%s\n' "$out" | grep -Fxc "1${TAB}https://example.com/g${TAB}GraceMark${TAB}grace")
[ "$matches" -eq 1 ] || fail "expected exactly one anchored bystander line, got $matches: $out"

ic=$(python3 -c "import sqlite3; print(sqlite3.connect('$DB').execute('PRAGMA integrity_check').fetchone()[0])" 2>&1)
[ "$ic" = "ok" ] || fail "integrity_check after the documented recovery-open: $ic"

# DROPPED after two explorations (claim discipline): at the file level this
# checker cannot distinguish a hot journal (data at risk) from an
# invalid-header journal sqlite documents as cold and may leave behind — the
# journal legs were an undocumented hygiene claim, not the declared property.
# The declared property (P1 metadata) is conservation + a well-formed db,
# carried by the two legs above. Journal-file hygiene is recorded in RESULTS
# as an observation, not asserted.

exit 0
```

## Recipe 5 — all or none, across files

`spike/dogfood/2026-10-14-mechanisms/apparatus/defines/useradd/check.sh`, the checker behind the 2026-10-14 mechanisms run's `useradd` FAIL (#861). `useradd` replaces `passwd`, `shadow`, `group` and `gshadow` one after another, each whole through a temporary and a rename, so a kill between two of them leaves every file intact and the four contradicting each other — and the built-in atomicity form, which judges each file on its own (`group` and `gshadow` old-or-new; `passwd` and `shadow` by their history form, which does not judge an appended tail), has nothing to say. Leg c counts the user across all four files and accepts four or none. Of the 71 explored worlds, 21 FAILed, and leg c was red in all 21; `pwck` (leg a) was red too in 7 of them and `grpck` (leg b) in another 7, and in the remaining 7 leg c alone saw it — which is why the count, not the tools' own consistency checks, is the leg to copy.

The checker also runs the recovery a user would run — the same `useradd` again, its "already exists" accepted — before it judges, and prints the legs before that too. A world the recovery heals then passes, and a world the recovery made worse would read differently before and after; this one read the same, which is how the run told a contradiction in the files from a recovery that damages them. It does that inside the checker rather than through `[recovery]`, which runs only on the saved FAIL exhibits ([docs/cli.md](cli.md)) and would not see the other worlds. Recipe 4's "the next open is the recovery" is the special case where reading is the recovery; here it is a command. The `CANDIDATES.md 1.1` in the header comment is the run's ordered candidate list, `spike/dogfood/2026-10-14-mechanisms/CANDIDATES.md`, and the target reached its verdict under `--observe syscalls`, the next step the default mode named (`oracle_missed_operation`).

`spike/dogfood/2026-10-14-mechanisms/apparatus/defines/useradd/check.sh`:
```sh
#!/bin/sh
# CANDIDATES.md 1.1. The recovery a user runs is the same useradd again ("already exists" accepted);
# the legs are read before it (printed only) and after it (judged).
set -u
S=${SIDEEYE_STATE_DIR:?}; R=$S/root; E=$R/etc
legs() {
    a=ok; b=ok; c=ok; d=ok
    pwck -r -q -R "$R" > /dev/null 2>&1 || a=FAIL
    grpck -r -R "$R" > /dev/null 2>&1 || b=FAIL
    n=0
    grep -q '^alice:' "$E/passwd" 2>/dev/null && n=$((n+1))
    grep -q '^alice:' "$E/shadow" 2>/dev/null && n=$((n+1))
    grep -q '^staff:[^:]*:[^:]*:.*\balice\b' "$E/group" 2>/dev/null && n=$((n+1))
    grep -q '^staff:[^:]*:[^:]*:.*\balice\b' "$E/gshadow" 2>/dev/null && n=$((n+1))
    [ "$n" = 0 ] || [ "$n" = 4 ] || c="FAIL($n of 4)"
    for l in 'root:x:0:0:root:/:/bin/sh' 'carol:x:1001:1001::/:/bin/sh'; do grep -qxF "$l" "$E/passwd" 2>/dev/null || d=FAIL; done
    for l in 'root:*:20000:0:99999:7:::' 'carol:*:20000:0:99999:7:::'; do grep -qxF "$l" "$E/shadow" 2>/dev/null || d=FAIL; done
    echo "a=$a b=$b c=$c d=$d"
}
echo "checker(useradd) before recovery: $(legs)"
timeout 60 useradd --prefix "$R" -M -d / -G staff -p '$6$s$h' -s /bin/sh alice > /tmp/useradd-recovery.txt 2>&1
rc=$?
[ "$rc" = 0 ] || [ "$rc" = 9 ] || echo "checker(useradd) recovery exited $rc: $(tail -c 200 /tmp/useradd-recovery.txt)"
after=$(legs); echo "checker(useradd) after recovery: $after"
case "$after" in "a=ok b=ok c=ok d=ok") exit 0 ;; *) exit 1 ;; esac
```

## Recipe 6 — the next run must still go through

`spike/dogfood/2026-10-14-mechanisms/apparatus/defines/alembic/check.sh`, the checker behind the same run's Alembic FAIL. With an `env.py` that does not apply the workaround SQLAlchemy's SQLite dialect documents, a batch migration on SQLite commits its temporary table alone — Python's `sqlite3` sends no `BEGIN` before DDL — and the copy, the drop, the rename and the version later. Killed between, nothing legs a, b and c read is wrong: the recorded revision, the table's shape and every row are whole (read after the recovery had been tried), and those legs passed in all 28 of the 43 explored worlds that FAILed; what is left besides is the temporary table, inferred from the two commits and seen in the state rebuilt by hand — the world's record lists no tables. Leg d, the recovery the user would run — the same `alembic upgrade head` — failed in all 28, and it was the only red leg in each. So the leg to copy is the next run's exit status, taken as part of the invariant rather than as a step before it. The database and its journal are declared `scratch` in `spike/dogfood/2026-10-14-mechanisms/apparatus/defines/alembic/sideeye.toml`: SQLite leaves them torn by design and repairs them on the next open (Recipe 4's contract), and without the declaration the built-in layer would judge those torn bytes itself — the reason the define gives, not something this run measured, since it declared them from the start.

Two things not to copy. Leg b picks the table shape it expects from leg a's input, the revisions recorded: when the version table holds none of the revisions the checker knows, b goes red with a. A version table naming a known revision beside another fails a — and d, since Alembic cannot upgrade from it — but not b: that is what the control for leg a built (`spike/dogfood/2026-10-14-mechanisms/transcripts/controls.txt`), so the coupling shows only in the case the controls did not build. The same run's Django checker had the same coupling and was fixed by counting only the migrations it knows (`spike/dogfood/2026-10-14-mechanisms/SELECTION.md`, "Checker controls"). And the recovery's output is cut to its last line (`tail -1`), which for SQLAlchemy is a link, so the world's record does not say which error the next run met. This one is shown as it ran, because the run's record is of these bytes.

```sh
# leg d. SQLite rolls back a hot journal on the first open, which that run makes.
set -u
S=${SIDEEYE_STATE_DIR:?}
export PYTHONDONTWRITEBYTECODE=1
legs() {
    python3 - "$S/app.db" <<'PY'
import sqlite3, sys
try:
    c = sqlite3.connect(sys.argv[1])
    vers = sorted(r[0] for r in c.execute("SELECT version_num FROM alembic_version"))
    a = "ok" if vers in (["r1"], ["r2"]) else "FAIL(alembic_version %s)" % vers
    cols = [(r[1], r[2].upper()) for r in c.execute("PRAGMA table_info(notes)")]
    shapes = {"r1": [("id", "INTEGER"), ("body", "TEXT")], "r2": [("id", "INTEGER"), ("text", "TEXT"), ("created", "INTEGER")]}
    b = "ok" if any(cols == shapes.get(v) for v in vers) else "FAIL(%s for %s)" % (cols, vers)
    label = "body" if ("body", "TEXT") in cols else "text"
    got = c.execute("SELECT id, %s FROM notes ORDER BY id" % label).fetchall()
    cc = "ok" if got == [(i, "note %d" % i) for i in range(1, 101)] else "FAIL(%d rows)" % len(got)
except Exception as e:
    a = b = cc = "FAIL(%s)" % type(e).__name__
print("a=%s b=%s c=%s" % (a, b, cc))
PY
}
echo "checker(alembic) before recovery: $(ls -l "$S" | awk 'NR>1{printf "%s=%s ", $9, $5}')"
timeout 120 python3 -m alembic -c /s/al-aux/proj/alembic.ini upgrade head > /tmp/al-recovery.txt 2>&1
rc=$?
d=ok; [ "$rc" = 0 ] || d="FAIL(exit $rc: $(tail -1 /tmp/al-recovery.txt | head -c 120))"
after="$(legs) d=$d"; echo "checker(alembic) after recovery: $after"
case "$after" in "a=ok b=ok c=ok d=ok") exit 0 ;; *) exit 1 ;; esac
```

## Failure patterns, each with the run that taught it

- **A broken state the recovery heals is no red.** A checker that runs the tool's recovery first has to be shown broken states the recovery cannot repair. In the 2026-10-14 mechanisms run, update-alternatives' first broken state for leg b pointed the link under its alternatives directory at the other editor; the checker's recovery, the same `--install`, put the link back, and the checker passed it — correctly — so the control said nothing about leg b until the broken state was one `--install` leaves alone (the generic link replaced by a plain file). The first form is recorded in prose, not in a transcript (`spike/dogfood/2026-10-14-mechanisms/SELECTION.md`, and the comment in `spike/dogfood/2026-10-14-mechanisms/apparatus/defines/alternatives/legs.sh`); the run's one-broken-state-per-leg controls are `spike/dogfood/2026-10-14-mechanisms/apparatus/controls.sh`, with their output in `spike/dogfood/2026-10-14-mechanisms/transcripts/controls.txt`.
- **Exit-0-on-unreadable.** todoman's `list` prints a traceback and exits 0 — it answers "nothing wrong" precisely when it could not look. The falsification gate refused it: the first real checker rejected as unfalsifiable, as opposed to a synthetic `/bin/true` (`BUILDLOG.md`, the todoman entry). The committed fix is a strict wrapper — exit 0 AND no error text in the output (`spike/dogfood-todoman.sh`).
- **Demanding destruction.** A checker that requires the operation to have visibly happened condemns correct crash recovery along with the bug (recipe 2). Allow the no-op; let a separate gate judge whether a fix gutted the feature.
- **Counting lines when you mean occurrences.** `grep -c` counts lines; devtodo rewrites its whole store onto one XML line, so a duplicated note still counted as 1. `spike/assisted/devtodo/ops/check.sh` counts occurrences instead (`grep -o` piped to a line count) and records the review finding that caught it.
- **Asserting what you did not observe.** The general shape behind all of the above: the claim and the observable truth must agree. Every blind-campaign checker under `spike/blind-hunt/`, `spike/blind-hunt2/` and `spike/blind-hunt3/` ships with a red suite beside it proving each leg can individually fail — the cheapest way to know a checker is load-bearing.
- **A scratch file is not a counterexample — and only a checker knows which is which.** git commit reaches a full verdict and FAILs at one crash point: COMMIT_EDITMSG, opened with truncation before the message is written, torn to empty by a kill in that window. It is not a git bug — git rewrites the file on the next commit and never reads a torn one — and L0 has no way to know a file is scratch (DESIGN §12's per-file atomicity exempts no file *by its role* — a scratch file is judged like any other). The taught fix: a target with scratch files needs a checker carrying the *real* integrity claim — the same run with `git fsck --connectivity-only` as the checker accepted every crash world, because git's actual durability (objects, refs, index) held in all of them. An L0-only FAIL on a scratch path is the tool doing what it is defined to do, and the checker is where the definition gets sharper. Measured 2026-08-11, git 2.39.5, thirty-four worlds; the run and the ruling live in issue #35 and the freeze audit's row for it. **A second example, Borg (cohort 2, 2026-08-21), shows the same shape arriving a different way: the target creates the scratch path and the measurement setup relocates it into the judged root. The define's r2 repointed `BORG_BASE_DIR` because worlds refused otherwise, which brought Borg's own client cache inside the state root the engine rolls back, and all three L0 violations landed in that cache's in-place rewrite. The recipe held without change: the checker carried Borg's real integrity claim (stale-lock removal, `borg check`, base conservation, old-or-new listing) and the contract held in all 119 worlds. One caveat worth carrying with the recipe — the checker also attempts the cache's documented deletion-and-rebuild first, but that `rm -rf` is unchecked and the committed drill shows it failing on permissions, so the evidence is the contract legs and not that leg. **The lesson the second example adds: when apparatus relocates state into the judged root, ask which of the relocated files the target's contract actually covers, and give the checker a leg for the ones it does not.** Adjudicated 2026-08-27 under #240; `spike/cohort2/borg-r3/RUNLOG.md` carries the ruling. **Reversed on 2026-09-03 (ADR 0043, #261): a define can now name its scratch paths** — `[define] scratch`, each entry the path itself and everything beneath it — and the built-in invariants judge none of them, in no world. The measurement above stands and so does the recipe's point: the checker is still the only thing that says the repository is *intact*; scratch only stops L0 and L1 from calling a torn scratch file a violation, and the report says which paths were left alone and how many recorded paths that was. "Exempts no file by its role" was true while a define had no place to say a role.
